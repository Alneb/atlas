# What in the core should be a plugin, and one reader on every device

The user (2026-10-19 ~23:30): *"you should do a deep review of all the code in the main app that should move to being a plugin (ej excalidraw), then we need to unify the android app and the desktop in terms of books manga audiobooks etc and polish the android plugins and the app itself so that its not only atlas, but an easy to use ebook reader, comic reader, pdf reader an annotator, and notepad"*.

This is the review: a read-only audit of the tree at `37ceb38c` (line counts from `wc -l`), against PHILOSOPHY.md §3 (*integrations are plugins; the core is generic*) and the plugin API as PLUGIN-API.md and `ui/src/lib/plugin-api.ts` (API 5) define it. The order of work at the end is the proposal; each move gets its own commit with the gate green.

## What a plugin cannot do yet (the gaps that block most moves)

### Stays in the core, and why

- **The PDF viewer and annotator** (`panes/Pdf.svelte` 365, `pdf-viewer.ts`, `pdf.ts`, `pdf-save.ts`, `pdf-place.ts`, `PdfThumbs.svelte`, `pdf_text.rs`): a PDF is a file type like a picture, and `[[x.pdf#page=…]]` is core link resolution — revisit only inside the reader unification below.
- **Tasks and calendar** (Obsidian Tasks compatibility, PHILOSOPHY §4; `task_suggest` is shared with the native capture box), **Today, the daily log and Home** (the extras already are plugins: `daily`, `home`, `weather`), **terminals, agent terminals, MCP, agents** (PHILOSOPHY §3 names them generic), **capture and its hooks**, **sign-ins / OAuth / the remote bridge / mirror**, **code-editor support** (LSP, VS Code themes), **web tabs**, **live editing** (`live.rs` is a relay; only `draw-live.ts` moves with #2), **e-ink mode**.
- **The git panel** (`git.rs` 567 + UI ≈550): debatable; it feeds Today's activity, the file tree and the editor gutter — moving it needs tree-decoration and gutter APIs, much work for little gain.
- **The Android pen and reading infrastructure** (`PageInk`, `InkStore`, `ReaderBars`, `PenView`, `PageSource`, `PenBar`, `OnyxInk`, `PenCatcher`; `atlas-pen`): the user's decision (REFACTOR-native-plugins.md): *"the eink tech should … be on the main app and the plugins call for it"*. `InkStore.pdf()` and `PageSource` hard-code the Excalidraw format — the coupling point if #2 moves.

## Excalidraw as the notepad plugin's web side — the plan for its assets (A3 applied)

What it needs from the core is now there; what remains is building and loading it as the plugin's files rather than the UI's.

1. **A build inside the plugin**: `plugins/beta/notepad/web-src/` with its own `package.json` (`@excalidraw/excalidraw`, `react`, `react-dom` move there from `ui/package.json`) and a library build (Vite `build.lib`, ES module, one entry `web-src/index.ts` exporting `mountDrawing(host, atlas, opts)`) that bundles React, Excalidraw and today's `draw-*.ts` / `pen-shapes.ts` / `linked-pages.ts` / `last-pages.ts` / `panes/Excalidraw.svelte` logic (rewritten without Svelte, or with Svelte compiled into the bundle). Output: `plugins/beta/notepad/web/excalidraw.js` (+ its chunks, `excalidraw.css`) and `web/fonts/` copied from `@excalidraw/excalidraw/dist/prod/fonts` (what `nodeAssets("excalidraw", …)` copies into `ui/dist/excalidraw/` today). The output is generated, git-ignored, and made by `node plugins/beta/notepad/web-src/build.mjs` — run by `docs/scripts/auto-install.sh` and the gate's `build` stage before the plugin is copied into a vault or packed (a plugin folder carries no build step of its own at install).
2. **The `inkStroke` patch moves with it**: `rewriteInk` / `INK_AT` go from `ui/vite.config.ts` into the plugin's build config, unchanged (the same `transform` and the same `buildEnd` failure when a new Excalidraw moved the code, and the `optimizeDeps` twin for its dev server); `globalThis.__atlasInk` stays the hook, set by the bundle's `draw-ink` part.
3. **Loading**: the plugin's `view.js` claims `*.excalidraw` / `*.excalidraw.md` (A1) and, on mount, sets `window.EXCALIDRAW_ASSET_PATH = atlas.assetUrl("web/")` (a folder's address; Excalidraw fetches `fonts/…` under it), adds `<link rel="stylesheet" href="${atlas.assetUrl("web/excalidraw.css")}">` once, and `await import("./web/excalidraw.js")` — loaded only when a drawing opens, its chunks by their relative imports, all through `/plugin-files/` (so a server vault and the phone get them the same way, revalidated by ETag). `registerEmbed(["excalidraw", "excalidraw.md"], …)` in `main.js` imports the same bundle for `![[x.excalidraw]]`.
4. **What the core drops then**: `ui/src/lib/draw-*.ts`, `panes/Excalidraw.svelte`, `NotepadBar.svelte`, the `excalidraw` pane kind and `specForPath` case, `builtin-embeds.ts`'s line, the `nodeAssets("excalidraw")` and `inkStroke()` entries of `ui/vite.config.ts`, React and Excalidraw from `ui/package.json` (the UI bundle loses ~2–3 MB), `ui/dist/excalidraw/`. The live room is `atlas.live.join` (A4), the pen's shapes `atlas.pen.shape` (A6); the server's save hook (A5) is the one gap still open.
5. **Watch out**: a library plugin is the right home for React only if a second plugin needs it — until then it stays inside the notepad bundle (one copy is already the case); the bundle must not touch the page's globals beyond `EXCALIDRAW_ASSET_PATH` and `__atlasInk`; e-ink and the Android WebView load the same files (no `blob:` workers: Excalidraw's own workers, if any, load by URL from `web/`).

## Proposed order of work

1. **Small moves with no new API** (each S/M, one commit each): `clip.rs` into the catalog engine (#3); Rnote's `draw.rs` and commands into the `rnote` plugin (#4); `web_filters.rs` into `atlas-app` (#9); `companion_tidy.rs` into its plugins or gone (#7, asked).
2. **References out of the core** (#1, #8): REFACTOR-libraries.md step 4.
3. **The editor contract (A1) and embeds (A2)** — the keystone: it lets a plugin be the default editor of a file type on the desktop, which the readers need too (`.epub`, `.cbz` open in Books / Manga on a click, as on Android). — **DONE** (2026-10-21; see A1, A2). Left for moving Excalidraw (#2): its pane kind, opener and `specForPath` case become the notepad plugin's `claims = ["*.excalidraw", "*.excalidraw.md"]` and view; `builtin-embeds.ts`'s line becomes the plugin's `atlas.registerEmbed`; the `#Page 2` anchor arrives as `atlas.anchor` / `pane.onAnchor` (today `openDrawingAt` / `drawingPages`); its save/dirty go through `atlas.pane`; then A3–A6 (assets and shared modules, live rooms, the server save hook, core endpoints).
4. **One PDF annotation store** — a decision for the user before any reader code: the companion drawing (`x.pdf.excalidraw`, what Android and the notepad write; DESIGN-native-book-reader.md "One paper") shown by the desktop's PDF pane too, or annotations in the PDF everywhere.
5. **Shared web modules (A3)**: one zip / EPUB / CBZ module for the books and manga web sides; then the readers' web sides reach Android's features (MOBI/FB2/TXT through the core, manga ink written). — **zip DONE** (2026-10-21: `plugins/beta/zip`, see A3). EPUB parsing stays in Books (only it reads EPUBs) and CBZ listing in Manga (`zipEntries`, a filter over `zipIndex`); a later shared module goes the same way (a library plugin, `requires`, a relative import).
6. **Excalidraw as the notepad plugin's web side** (#2, after A1–A6): one `notepad` plugin with a web side and an Android side; compaction and page rules in one Rust crate both link.
7. **Audiobooks**: a player (new): the Audiobookshelf server's books played in Atlas on both platforms — scope to ask.
8. **The Android app as a reader first** (*"not only atlas, but an easy to use ebook reader, comic reader, pdf reader an annotator, and notepad"*): a launcher that opens on the library (books / comics / PDFs / notebooks) rather than the workspace, a file picker for files outside the vault, open-with from other apps — designed with the user.
