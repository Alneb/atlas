# Plugins — special-purpose views live with the workspace, not in Atlas

Added 2026-10-06. The Runs tab was too specific: code that applies to nothing else is hard to maintain in the main
app, so it was decoupled. Where it lives: **as a plugin in the vault that uses it** (a research vault with simulation runs).

## Before / after
| | before (slice 5, `c811314`) | after |
|---|---|---|
| indexer | `crates/atlas-core/src/runs.rs` (269 lines) + `GET /api/runs` + `[runs]` config section + generated `Run*` types | `<vault>/.atlas/plugins/runs/index.py` (stdlib Python, same rules and per-folder cache) |
| view | `ui/src/panes/Runs.svelte` + `lib/runs-api.ts`, pane kind `runs`, action `ui.runs`, rail entry | `<vault>/.atlas/plugins/runs/view.js` + `view.css` (plain ES module, no build step) |
| tests | `ui/tests/runs.spec.ts` (needed a real run copied from a real vault) | `ui/tests/plugins.spec.ts` (a fixture plugin: the system, not runs) |
| `scripts/vault/runs_index.py` | standalone copy of the rules | removed; `<vault>/.atlas/commands/runs.index.toml` runs the plugin's `index.py --md runs/RUNS.md` |

Atlas itself now contains **no runs-specific code**. What it gained is generic: one module, one pane kind.

## A plugin
A folder `.atlas/plugins/<id>/` (id: letters, digits, `-`, `_`) in the workspace:
```toml
# plugin.toml — only `title` is required
title = "Runs"
description = "simulation runs: parameters, sweeps, tables, figures, compare"
icon = "table"            # an app icon name; unknown → a generic plugin icon
keys = "Ctrl+Alt+R"       # default shortcut; rebindable in the Commands pane like any command
view = "view.js"          # default
data = "python3 \"$ATLAS_PLUGIN_DIR/index.py\""   # optional; cwd = workspace root
timeout_secs = 120        # optional (default 30)
[settings]                # free-form; handed to the data script and to the view
dir = "runs"
```
- **View**: an ES module whose default export is `mount(host, atlas)`; it may return a cleanup function (or a
  promise of one). It draws into `host` with plain DOM and styles itself with the app's CSS variables
  (`--bg --bg-elev --bg-hover --text --text-muted --text-faint --accent --accent-soft --border --radius
  --font-mono --ui-scale`), so it follows the theme.
- **`atlas`** (`PluginApi`, `ui/src/lib/plugins.svelte.ts`) — deliberately small, because plugins outlive
  refactors: `plugin` (its manifest, incl. `settings`), `data(args)` (runs the data script → its JSON),
  `open(path, line?)`, `openTable(path)`, `readText(path)`, `fileUrl(path)` (object URL fetched with the API
  header — images, PDFs), `onFilesChanged(fn)` (unsubscribe returned), `toast(title, body?, kind?)`.
- **Data script**: stdin = `{"settings": {...}, "args": <what the view passed>}`, stdout = JSON, stderr = its
  log. Runs through the same runner as workspace commands (`sh -c`, process group killed on timeout), with
  `$ATLAS_ROOT` and `$ATLAS_PLUGIN_DIR` exported. `POST /api/plugins/{id}/data`.
- **Discovery**: `GET /api/plugins` lists every folder with a `plugin.toml`. A manifest that does not parse is
  listed with its error and shown as a toast ("Plugin broken not loaded: …"), never silently skipped.
  Each plugin becomes a palette command (`plugin.<id>`), a rail button after the built-ins, and a `plugin`
  pane (`{ kind: "plugin", id, title, icon }` — title/icon travel in the spec so restored layouts label the tab).

## API v2 — the shared context and the data substrate (2026-10-07, docs/design/MALLEABLE.md R3)
Additive; v1 plugins keep working.
- `context()` → a snapshot of what the user is looking at: `active` / `open` panes, the editor `selection`
  (path, lines, text), the caret's `section` (`{ path, heading, line }`), and `hover` (`{ path, line?, source }`).
- `onContext(fn)` → called with a snapshot on every change (also while the plugin's tab is hidden); returns
  the unsubscribe function.
- `hover(path | null, line?)` → point at a note: Base rows, board cards and `[[links]]` in notes light up,
  as they do for Atlas's own views (Embark's hover sync).
- `writeProperty(path, key, value)` → rewrites one frontmatter key (an array value → a YAML list), through
  `PUT /api/property`.
- `query(baseYaml, thisPath?)` → evaluates Bases YAML (filters, formulas, views) over the workspace's notes,
  with no `.base` file needed (`POST /api/base/query`). It returns the same typed rows as a `.base`.
Source: `ui/src/lib/context.svelte.ts` (the one context, which used to be `uistate.ts`; still pushed to the
core for `atlas mcp`) and `ui/src/lib/plugins.svelte.ts`. Tested by `ui/tests/context.spec.ts`.

## Iterating
Edit `view.js`, `view.css` or the data script and an open plugin pane remounts by itself (fs events under the
plugin folder, 250 ms debounce; a fresh blob URL per load defeats module caching); editing `plugin.toml`
reloads the list (new shortcut, title, icon). No Atlas rebuild, ever — "easy to iterate" for the user and for
any Claude session, which can write a plugin as files.

This needs the core to watch the plugin folders: `.atlas` is a dot-folder, which the vault walk skips, so at first nothing under `.atlas/plugins/<id>/` sent an event and edits applied only after a restart. `events.rs` now watches every folder under `.atlas` except `cache/` and `trash/` (`all_dirs`, test `plugin_folders_are_watched`). On the UI side (`watchPlugins`): a `main.js` / `view.js` / `.css` / `.json` change re-runs the plugin's main; a `plugin.toml` change, or a plugin folder appearing or going, reloads the list; a change to the helper's own script (`.py`, `.sh`, `.rb`, `.pl`, `.lua`, …) stops the helper, and the next call starts the new code. That drops the helper's state (the SSH plugin's open sessions; its shared ssh connection survives, it belongs to ssh). Only the Rust core needs a rebuild.

## Trust
A plugin's view runs inside the app page with the same API the UI has (it can run commands), and its data
script runs as the user — the same trust as `.atlas/commands/*.toml` scripts: **the workspace is trusted**.
Do not open a workspace you did not create without reading its `.atlas/`.

## Watch out
- The UX audit's runs journey (`ui/ux/journeys.spec.ts`) presses Ctrl+Alt+R and expects `.row`
  and an "Open table" button — the plugin keeps all three, but `ux/workspace.ts` must also copy
  `.atlas/plugins/` into its sample for that journey to find the plugin.
- `runs/` is usually on the ignore list, so file events never fire there: the Runs view refreshes on `r` /
  Refresh (the cache makes that ~30 ms).
- The vault's `.gitignore` ignores `runs/` anywhere; `!/.atlas/plugins/runs/` re-includes the plugin folder.


## v3 — pieces, not apps (2026-10-08)
Full design and measurements: [REFACTOR-plugins-v3.md](../refactor/REFACTOR-plugins-v3.md). In short:
- `main.js` with `export function register(atlas)` runs at startup and **again on every save**. It registers blocks
  (`registerBlock("runs.plot", (host, {options, note, props}) => cleanup, {title?, options?})` — `options` lists the block's options as form fields, `{ key, label, hint?, kind }` with `kind` one of `text`, `number`, `toggle`, `list` (comma-separated, written as a YAML list) or `choice` (with `choices: [...]`); a page then offers "Options…" for the block), commands (`registerCommand`) and entity
  kinds. All of it is undone on reload or switch-off.
- `view.js` (a pane) is optional; the rail button is opt-in (`rail = true`).
- Composition: `mountBlock(host, {type: …})` draws any block; `other(id)` → another plugin's settings and data.
- Helpers: `thumbUrl(path, w)` (core-made thumbnails: never show full-size figures small), `table(path)` (any
  size), `plot(host, {x, ys, xLabel, yLabels})`, `noteProps(path)`, `createFile(path, text)`.
- Switch a plugin off: Settings → Plugins & automation (`[plugins] off`).
- More API: `pick(req)` (the palette chooser), `registerSuggestion(fn)` (offer a view for the section
  under the caret), `path` (the file a pane was opened with); manifest `opens = ["*.tsv"]` makes the pane an
  "Open with…" choice. `.atlas/init.js` is a plugin without a manifest (`register(atlas)`, reloads on save).

## Built-in plugins (the Library)

Zotero moves to a plugin as well, and the leftmost panel separates the core icons from the plugins' icons. A plugin can execute code so that it is fast, and the papers Library is kept separate because it serves scientific work, not every way of using the app.

**What was built.** A *built-in plugin* is a part of Atlas that is not for every vault. It is listed in `ui/src/lib/builtin-plugins.ts` (`BUILTINS`; today one entry, `library`) and switched exactly like a vault plugin: its id in `[plugins] off` of the vault's `.atlas/config.toml`, by the same switch in Settings → Plugins & automation. While it is off, nothing of it exists in that vault:

| part of the Library | how it is gated |
|---|---|
| the command "Library (papers)" and its shortcut | the action carries `plugin: "library"`; `allCommands()` drops such actions while the plugin is off, so the palette, the key bindings and toolbars lose it together |
| the toolbar button | the `plugins` word of a toolbar draws the built-in plugins that are on, then the vault's plugins, in the same row as the app's own buttons (until 2026-10-14 a divider set them apart; write `divider` in the toolbar for one). The default sidebar no longer lists `ui.library` among the core tools (a toolbar file that still names it keeps that one button, not two) |
| `@` and `\cite{` completion | `citing()` in `editor/create.ts` |
| the Zotero browser connector (a listening port) | `server.rs`: started only if `refs.connector` and the plugin is on |

**A vault Atlas creates** ("create vault" in the chooser, a folder that did not exist) starts with `off = ["library"]` (`vaults::start_plain`): a personal vault has no papers Library until it is switched on. An existing folder is never given a config this way, and an existing research vault keeps the Library.

**Why the native code stays in the core.** The Library's heavy parts (`refs.rs`, `connector.rs`, PDF text and thumbnails) are Rust and must stay fast; a vault plugin today is JavaScript plus a data script started per request, which is too slow for importing and listing a few thousand papers. So "separate" is done at the level that matters to someone not doing science — no button, command, completion or open port — while the code ships in the binary. **Not done, and the honest next step if more built-ins or third-party fast plugins are wanted:** a native helper per plugin (a long-lived process named in `plugin.toml`, spoken to over stdin/stdout with JSON, started when the plugin is on and stopped when it is off). With that, `refs.rs` could move out of the core into `plugins/library/` as its own crate. It is a design of its own (lifecycle, crash handling, sandboxing, packaging the helper for each platform) and was not started.

**Adding another built-in plugin**: one entry in `BUILTINS`, `plugin: "<id>"` on its actions, and a `builtinOn("<id>")` check wherever it hooks into the editor or the core. Tests: `ui/tests/library-plugin.spec.ts`, `a_vault_atlas_creates_starts_without_the_library…` (core).

The whole design, with what is still a proposal: [REFACTOR-plugins-v4.md](../refactor/REFACTOR-plugins-v4.md). Built so far:

- **`atlas.shell.menu(where, fn)`** — rows in the app's right-click menus. `where` is `"file"` (the file tree), `"tab"` (a tab or a pin in the left bar), `"editor"` (the text), `"block"` (a block's menu on a page) or `"terminal"` (the terminal's "+" menu, under Shell and Claude session: the SSH plugin puts one row per host there). `fn(target)` returns the rows for what was clicked, or nothing; `target` is `{ path, dir }` for a file, `{ path?, kind }` for a tab, `{ path, selection }` for the editor, `{ type, note }` for a block. A row is `{ label, run, icon?, hint?, detail?, danger?, disabled? }` (`icon`: an app icon name, ignored when unknown). Plugin rows come after the app's, under a separator; a builder that throws loses only its own rows (the error is in the console). Undone on reload and switch-off like every registration. Code: `ui/src/lib/plugin-menus.ts` (the lists and `pluginMenu(place, target)`), one `...pluginMenu(…)` in each of the four menu builders. Test: `plugin-menus.spec.ts`. Example: `plugins/examples/wordcount/main.js`.
- **`atlas.shell.statusItem({ id, text, title?, run? })`** — a cell in the status bar, left of the vim mode. With `run` it is a button. It returns `{ set(text, title?), remove() }`; the cell goes away on reload or switch-off. Text longer than 28 characters is cut with an ellipsis: a status cell is a word or a number, not a sentence. Code: `ui/src/lib/plugin-status.svelte.ts` (the list) and `StatusBar.svelte` (draws it). Same test.
- **Installing, updating, removing — always a copy in the vault.** Decided 2026-10-14: plugins are copied into each vault. A plugin lives in the vault that uses it, `.atlas/plugins/<id>/`; there is no machine-wide plugin folder. So a vault is complete on its own, travels with its plugins, and its git tracks them.
  - `atlas plugin install <folder | git address | .zip / .tar.gz> [--id name] [--on]`, or **Install…** in Settings → Plugins & automation. A folder is copied (without `.git`, `node_modules`, `target`, `__pycache__`); a git address is cloned and its `.git` dropped (it is a copy, not a checkout); an archive is unpacked (one top folder is fine). The manifest must be one this Atlas reads **before** anything in the vault changes. The id is the last part of the path or address unless `--id` says otherwise.
  - **It arrives switched off** — the setting is written *before* the plugin's folder appears, so a running Atlas never starts it, not even for a moment (it did, until a spec caught it on 2026-10-14) — and the answer says what it may do ("It may talk to …"): read it, then switch it on. `--on` skips that for a plugin you wrote.
  - `atlas plugin update <id>` (or the ↻ button): installs again from where it came — written by the install into `.atlas/plugins/<id>/.source` (`kind`, `from`, the date, the git commit). **The vault's own `[settings]` are kept** over the new manifest's; it stays on or off as it was; a running helper is stopped first. The copy it replaces goes to `.atlas/trash/<time>/.atlas/plugins/<id>/`.
  - `atlas plugin remove <id>` (or ✕): the folder moves to `.atlas/trash/`. **Nothing is ever deleted** by these commands.
  - `atlas plugin list`: each plugin, on / off / broken, its version, what it may do, and where it was installed from (so `atlas plugin update <id>` can be run on it).
  - Code: `crates/atlas-core/src/plugin_install.rs`; the CLI in `crates/atlas/src/main.rs`; routes `POST /api/plugins/install`, `/api/plugins/{id}/update`, `/api/plugins/{id}/remove`. Tests: three in `plugin_install.rs` (folder, update keeping settings, archive, and git with a local repository), `plugin-install.spec.ts`.
- **`atlas.helper` — a program of the plugin's own that stays running.** This is the answer to *"you could make plugins execute code so that they are fast"*: a plugin names a program in its manifest, in any language, and the core runs it for as long as the plugin is used.
  ```toml
  [helper]
  run = "python3 -u \"$ATLAS_PLUGIN_DIR/helper.py\""   # or a compiled binary in the plugin folder
  ```
  - **The protocol** (all of it): one JSON object per line, both ways. The core writes `{"id": 7, "method": "search", "params": …}`; the helper answers with a line carrying the same id, `{"id": 7, "result": …}` or `{"id": 7, "error": "why"}` (or `{"error": {"message": "why"}}`). A line **without** an id is an event, `{"event": "new-mail", "data": …}`, passed on to the page. stderr, and any line that is not JSON (a forgotten `print`), go to the plugin's log file `.atlas/cache/plugins/<id>.log`. Flush after every line (`python3 -u`, `flush=True`).
  - **From the plugin:** `await atlas.helper.call("search", { q })` (`{ timeout }` in seconds, default 60); `atlas.helper.on("new-mail", (data) => …)`; `await atlas.helper.state()` → `stopped` / `running` / `crashed`; `await atlas.helper.restart()`. The event `helper:exit` is sent when it stops.
  - **Its life** (`crates/atlas-core/src/helper.rs`): started by the first call, with the vault as its folder and `$ATLAS_ROOT`, `$ATLAS_PLUGIN_DIR`, `$ATLAS_PLUGIN_CACHE` (a folder of its own under `.atlas/cache/plugins/<id>/`, for large results: write a file there and answer with its path) set; in its own process group. When it exits, the calls waiting on it fail with the reason (nothing hangs) and the next call starts a new one. One that has been started five times in ten minutes is left stopped ("crashed") with a message pointing at its log, until `restart`. It is stopped when the plugin is switched off and when Atlas exits. A call that gets no answer in time fails; the helper is not killed for it.
  - **Honest limits:** started lazily only (no "start with the plugin" yet); a request cannot be cancelled; a helper that listens on a network port does not have to declare it yet.
  - Tests: `a_helper_stays_alive_between_calls_sends_events_and_is_restarted_after_it_dies`, `a_helper_that_keeps_dying_is_left_stopped` (core, with a 15-line Python helper); `plugin-helper.spec.ts` (from a plugin: two calls answered by one process, an event reaching the page, stopped with its plugin).
- **What a plugin may do is shown.** Settings → Plugins & automation writes under each plugin, in plain words, what its manifest asks for outside the page: "May talk to links.example.org · keep secrets (outside the vault) · run a program of its own." It is a list to read, enforced by the core for the network and secrets; **it is not a sandbox** (decided 2026-10-14): a plugin's JavaScript runs in the app's page. Read a vault's `.atlas/plugins/` before opening a vault that is not yours.
- **`atlas.fetch(url, init?)` — the network, through the core.** The request is made by the core (`crates/atlas-core/src/plugin_net.rs`, `POST /api/plugins/{id}/fetch`), not by the page: no CORS, a timeout (30 s; `timeout` in seconds, at most 300), a size limit (8 MB as text), and **only to hosts the manifest lists**:
  ```toml
  [permissions]
  net = ["links.example.org", "*.arxiv.org"]   # a host, or any host under one (not the bare domain)
  secrets = true                                # may keep secrets
  ```
  `net = ["*"]` is every host (what a clipper needs); Settings then says "may talk to any server on the network". A host that is not listed is refused before anything is sent, and the error says which line to add. A redirect is followed only to a listed host (an allowed server cannot hand the plugin on to another). Only `http` and `https`. The answer is like the browser's: `{ status, ok, headers, url, text(), json() }`; a 404 is an answer, not an error. Three additions: a header may be `{ secret: "token", prefix: "Bearer " }` — the core fills in the plugin's secret, so the token is never in the page; `body` may be an object (sent as JSON); `saveTo: "covers/x.jpg"` writes the body to `.atlas/cache/plugins/<id>/covers/x.jpg` (and nowhere else) and returns that path as `saved`, for pictures and other large or binary answers (then shown with `fileUrl` / `thumbUrl`).
- **`atlas.secrets`** — `get(name)`, `set(name, value)`, `delete(name)`, `has(name)`: this plugin's secrets in this vault, **kept outside the vault** so they are never in its git or its sync: `~/.config/atlas/secrets/<vault folder name>-<hash of its path>.json`, readable only by the user (file 0600, folder 0700), one table per plugin (`crates/atlas-core/src/secrets.rs`). A plugin sees only its own; a vault only its own. Needs `[permissions] secrets = true`. **Honest limits:** it is a file, not the desktop keyring (the keyring can replace it behind the same three functions; not done — it needs a system service that a headless `atlas serve` does not have); and `get` hands the value to the page, so prefer the `{ secret }` header, which does not.
- Tests: `hosts_are_matched_exactly_or_under_a_star`, `a_plugin_reaches_only_the_hosts_it_declared_and_its_secret_is_filled_in_by_the_core`, `secrets_are_kept_per_vault_and_plugin_in_a_file_only_the_user_can_read` (core, against a local one-request server); `plugin-net.spec.ts` (the whole path from a plugin, and that the page itself never talks to the server).
- **`atlas.openView(arg?, { title?, icon?, beside? })`** — opens the plugin's own pane (`view.js`) in a tab, or shows the one already open on that `arg`; the pane reads `atlas.arg`. A pane spec carries `arg` (`{ kind: "plugin", id, arg }` in `panes.ts`; the pane's id is `plugin:<id>#<arg>`), so each value is a tab of its own and survives a restart with the layout. Made for the SSH plugin's Files pane (one tab per host, another per remote file read) — without it a plugin had exactly one pane and no way to open it from its own code.
- **`atlas.shell.sideTool({ id, title, icon?, mount })`** — a tool of the plugin's in the side panel, beside Files / Search / Outline / Git. `mount(host)` draws it and may return its cleanup. It also adds the command "Side panel: <title>" (bindable). It works in both homes of the panel: beside the editors it is a tab of the side column; in the left bar its button joins the row of the four built-in tools. How: a side tool **is a block** (type `<plugin id>.<id>`) that says it belongs to the side zone — `ui/src/lib/side-tools.svelte.ts` holds the list; `specZone(spec)` in `panes.ts` answers "side" for a block that is a side tool and the dock places it by that (`panelZone(p)` for an open panel; before, the zone came from the pane's kind alone); the side panel's choice (`sidePanel.kind`) is a `SideId`: one of the four kinds, or `tool:<block type>`, kept in the vault's `shell.json` like before (a tool whose plugin loads later is waited for, as any plugin block). Test: `plugin-side-tool.spec.ts`.
- **`atlas.on(type, fn)`** — events. `file:open` (a tab newly opened on a file: `{ path }`), `file:save` (`{ path }`), `file:create` (a new note: `{ path }`), `file:rename` (`{ from, to }`), `file:delete` (`{ path }`), `capture` (`{ path, text }`), `command` (`{ id }`: any command run by a key, the palette, a toolbar button or a bookmark — told from `allCommands()` in `keymap.svelte.ts`, the one list every way of running a command takes it from). They are sent from the places everything passes through — the API client (`api.putFile`, `api.newNote`, `api.move`, `api.trash`, `api.capture` in `ui/src/lib/api.ts`) and `open` in `dock.ts` — so no pane announces anything itself. They are about what is done **in Atlas**; a file changed by another program still arrives through `onFilesChanged`. Listeners run after the action has finished (a microtask later) and inside the guard, so a listener can neither delay nor break a save. Writes under `.atlas/cache/` (the layout, recent files) are not announced. Code: `ui/src/lib/plugin-events.ts` (the typed union `PluginEvent`; an unknown name throws at registration). Test: `plugin-events.spec.ts`. **Not yet:** `app:start`, `vault:switch`, a schedule tick.
- **`atlas.editor.registerFence(name, render)`** — a fenced code block drawn by the plugin: write ```` ```statblock ```` in a note and the plugin's `render(host, { source, path, props })` draws it, in live preview and in the reading view; `source` is the text between the fences, `path` the note, `props()` the note's properties and the section's (`key:: value`). It returns a cleanup like a block. How it is built (`ui/src/lib/fences.ts`), and why this way: the markdown renderer is **not** told about fences. A fence is rendered as the code block it is (`<pre class="hljs">` with its language label), and `hydrateFences` — called from `hydrateBlocks`, so by the editor's rendered blocks and by the reading view alike — hides that code block and puts the plugin's drawing right after it. So: a fence nobody draws stays a code block; a plugin that loads after the note, is edited, or is switched off needs no re-render and no cache clearing (each mounted fence watches its name); and nothing about how Atlas renders Obsidian markdown changed. A renderer that throws shows its message in place and gets a line in the plugin's log. In live preview the source appears when the caret enters the fence, as for every rendered block. Names: letters, digits, `-`, `_`; the last plugin to register a name draws it. Test: `plugin-fence.spec.ts` (a stat block; also that a `main.js` added to an existing plugin folder is now picked up at once — it was not: `watchPlugins` only followed files it already knew).
- **The other editor hooks** (`ui/src/lib/editor/plugin-hooks.ts`; one line in `create.ts`: `pluginHooks(path, md)`):
  - `atlas.editor.registerCompletion({ where?, trigger?, complete })` — `complete({ path, line, before, word })` returns `[{ label, detail?, insert?, kind? }]` or a promise of it. With `trigger` (a regular expression or a text) the source is asked only when the text before the caret ends like that, and an accepted item replaces what the trigger matched (`@npc:br` → `[[Brok]]`); the plugin decides what fits. Without a trigger it is asked after two letters and the typed word filters the labels. In notes it is one more source of the list that already has links, slash commands and citations; in code files it joins the language's own.
  - `atlas.editor.registerKey("Ctrl+Alt+J", run, where?)` — `run({ path, line, selection, replace(text), insert(text) })`. It comes before the app's keys and vim's; returning `false` lets the key go on. Keys are written as everywhere in Atlas and matched by physical key (`lib/keys.ts`), so they work on a Spanish layout.
  - `atlas.editor.onPaste(fn)` / `onDrop(fn)` — `fn({ text, html, files, path })` returns the text to insert instead, or `null` ("not mine"). The first handler that answers wins. A handler may answer later (a promise): the paste is then held, and the plain text is inserted if it comes back with nothing or fails.
  - `atlas.editor.registerDecoration(pattern, render)` — for every match of the regular expression in the visible text, `render(match)` returns `{ class?, title? }` (a mark on the text) or `{ replace(host) }` (a drawing instead of the text; the text shows again while the caret is in it). Overlapping matches: the first wins — the editor refuses overlapping replacements, and one that throws would take down every decoration.
  - `atlas.editor.extension(ext)` with `atlas.editor.codemirror` (`{ state, view }`: the app's own copies of `@codemirror/state` and `@codemirror/view`) — **the escape hatch**: any CodeMirror 6 extension, built from those modules (an extension made from another copy of the library is refused by the editor). It is unstable by nature: it follows the editor library, not Atlas. Each one is first tried on an empty document: something the editor refuses is logged against its plugin and never reaches a real editor (without that check, one bad extension stopped every editor from opening — the spec caught it).
  - How they stay cheap and safe: completions, keys and paste handlers are looked up in module-level lists at the moment of use, so a plugin coming or going rebuilds nothing; only decorations and raw extensions are pushed to open editors (a refresh effect, and one compartment per editor). Every plugin function goes through `guard`. Test: `plugin-editor.spec.ts`.
- **`atlas.terminal.run(command)`** — types the command into the shell terminal and enters it; the terminal is opened when there is none. It is deliberately not a hidden process: a "Run" button should leave the command where it can be read, changed and run again (↑), with its output. For a process whose output the *plugin* wants, use the helper. Code: `runInTerminal` in `ui/src/lib/actions.ts`; a terminal's handle gained `run` (`Terminal.svelte`).
- **Settings from a schema — no TOML by hand.** A plugin declares its settings in `plugin.toml`:
  ```toml
  [[setting]]
  key = "sides"            # the name in [settings] and in atlas.plugin.settings
  label = "Sides"          # default: the key
  kind = "number"          # text · number · toggle · list (several texts) · choice (with choices = [...]) · secret
  hint = "of the die rolled by default"
  default = 6
  ```
  Settings → Plugins & automation then shows a **Settings…** button for the plugin: a form with one control per field (the same dialog and field code as a block's options, `BlockOptions.svelte`). Saving writes the values into `[settings]` of the same `plugin.toml` with the file's comments and layout kept (`plugins::save_settings`, `PUT /api/plugins/{id}/settings`); the plugin reloads and reads them from `atlas.plugin.settings` as before. Rules: a field left empty, or set to its default, is taken **out** of the file, so `[settings]` says only what was chosen and the default applies; `settings` handed to the plugin (and to its data script) always has the defaults filled in; a key that is not declared, a value of the wrong kind or outside `choices` is refused and nothing is written. Keys in `[settings]` that have no `[[setting]]` stay as they are (free-form, edited as text). `version = "0.2.0"` in the manifest is shown next to the plugin's name. Tests: `declared_settings_have_defaults_and_are_saved_into_the_file_without_losing_its_comments` (core), `plugin-settings.spec.ts`. A field of kind **`secret`** (a token, a password) is typed blind and never shown back: its value goes to the secret store outside the vault (`atlas.secrets`, below), never into `plugin.toml`; the form says "Set" or "Not set yet", and leaving it empty keeps what is stored. It needs `[permissions] secrets = true`. Not yet: the kinds `folder` and `file`.
  **Lists of records, `when` and `group`** (asked for the mail accounts; meant for any list of things a plugin keeps, SSH hosts next). A field of kind **`records`** is a list of cards, each card a set of fields of its own (`fields = [ { key, kind, … }, … ]`, every kind but `records` again): `[[settings.<key>]]` tables in `plugin.toml`, the first card being the main one. The form draws a card per record — its name as the title, a "main" badge on the first, "Make main" (to the top) and ✕ (asks first) on the others, "Add …" (`add = "Add account"`) for a new card whose name field takes the keys. A card is named by its field `name` (or the key `name = "…"` says; added as a plain text field when the manifest does not declare it): unique, `[A-Za-z0-9_.@-]+`, and **fixed once saved**, because a card's secrets are kept under it as `<key>.<name>.<field>` — renaming is removing the card and adding another. Saving replaces the whole list (its order is the cards' order); the secrets of a card that is gone are forgotten. Buttons: `actions = [{ label, command, when? }]` on each card and `list_actions = [{ label, command }]` under the list run one of the plugin's own commands (`registerCommand`) with `{ setting, record }` / `{ setting }` — **after saving the form**, so the command sees what was typed. Any field, top-level or in a card, may carry `when = { auth = "outlook" }` (or a list of values; a switch takes `true` / `false`): it is drawn, saved and given its default only while the sibling field has that value (its default when unset) — a hidden field is taken out of the file when the form is saved, except a hidden records field, which is left as it is. `group = "Servers"` draws the fields of that name together under a heading that starts closed and lists what is inside. `readonly = true` on a secret: shown as "Set" / "Not set yet", never typed (a sign-in token the plugin keeps itself). A manifest that puts a key on the wrong kind (`choices` on a text field, `fields` on anything but records), nests records, or names in `when` a field that is not beside it, is listed with that error and not loaded. Core: `plugin_settings.rs` (the schema types — `SettingKind` is an enum that carries `choices` and the records' parts, `RawField` → `SettingField` checks a manifest's field —, `with_defaults`, `apply` = what saving writes); UI: `lib/plugin-settings.svelte.ts` (the open form, the core's fields as the form's), `components/settings/PluginSettings.svelte` (the dialog, mounted once in `App.svelte`, so `atlas.plugin.openSettings()` and the Plugins page open the same one), `FormFields.svelte` + `RecordCards.svelte` (the controls; `when` and `group` work in block options too). The dialog is wider when a plugin has records, and a card puts labels beside the controls. A plugin may save its own settings with `atlas.plugin.saveSettings(values)` (the same route; `null` takes a key out, also one it no longer declares — how a plugin moves old settings into new ones, as the email example does). Tests: `plugin_settings.rs` (manifest checks, `when`, cards saved and read back with defaults, refusals), `records_keep_their_secrets_by_card_forget_them_with_the_card_and_survive_an_update` (`plugins.rs`), `plugin-records.spec.ts`, `example-email.spec.ts`.
- **Versions.** `atlas.version` is the plugin API's number (4). In the manifest, `api = 4` says which API the plugin was written for and `needs = ">=0.3"` the oldest Atlas it works with; when this Atlas is older than either, the plugin is listed in Settings with the reason ("needs Atlas 0.3 or newer; this is 0.1.0") and nothing of it is loaded. Versions are compared as numbers, part by part (`0.10` is newer than `0.9`). Core: `plugins::too_old_for`, `API_VERSION`; test `a_plugin_that_needs_a_newer_atlas_is_listed_with_the_reason_and_not_loaded`.
- **A log per plugin, and a guard around every callback.** `ui/src/lib/plugin-log.svelte.ts`: `guard(pluginId, where, fn, fallback)` runs a plugin's function; a throw or a rejected promise becomes a line in that plugin's log (`logPlugin`) and the caller gets `fallback`, so one broken plugin costs only its own row, cell, command or block. Guarded so far: `register` in `main.js`, commands, menu builders and their rows, status cells, and a block's `mount` (which still shows its error where the block stands). (A trap met while building it: `const lines = (state[id] ??= [])` hands back the plain array, not the one the reactive state keeps, so the first line of every plugin was lost — read it back from the state after assigning.) Settings → Plugins & automation shows "N problems since Atlas started" under the plugin, with the time, the place and the message of each, and a Clear button. The list is **not** emptied when the plugin reloads: plugins reload for reasons that have nothing to do with their code (any change of the plugin list), and a first version that cleared on reload lost the evidence within a second (caught by the spec). The same failure repeated is one line; at most 50 lines are kept. The log is in memory: it does not survive a restart (a file under `.atlas/cache/plugins/` comes with the helper, whose stderr goes there too). **Rule for new hooks: never call a plugin's function directly — call it through `guard`.**
