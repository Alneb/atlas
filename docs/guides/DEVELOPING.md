# Developing Atlas — how the app itself is changed

For changes to Atlas's own source (this repo). To extend Atlas *from a vault* without touching the source, read [EXTENDING.md](EXTENDING.md) first — most needs end there. Its goal: the code can be maintained by anyone, without depending on whoever (or whichever agent) wrote it.

## The five concepts

Everything in Atlas is one of these. A change that needs a sixth is probably wrong.

| concept | meaning | where |
|---|---|---|
| **file** | the only truth; nothing lives only in the app. `.atlas/cache/` is deletable | the vault |
| **block** | anything drawn; mounts in a note, a page, or a tab | `ui/src/lib/blocks.ts` (registry), `ui/src/lib/views.ts` (row views) |
| **note view** | a whole note drawn by a plugin instead of its text (a mail note as the mail), chosen by the note's `view` property or its `type`; the editor stays loaded underneath, "Show as note" switches per note | `ui/src/lib/note-views.svelte.ts` (registry), `ui/src/panes/Editor.svelte` (draws it) |
| **command** | anything done; the same id works in the palette, on a key, from the CLI, over HTTP | `ui/src/lib/actions.ts` (UI), `crates/atlas-core/src/commands.rs` (core + vault scripts) |
| **context** | what the user is looking at: active file, selection, section, hover | `ui/src/lib/context.svelte.ts` |
| **plugin** | a folder in a vault that registers blocks and commands | `ui/src/lib/plugins.svelte.ts` (starting, watching), `plugin-registry.svelte.ts` (the list, what each registered), `plugin-commands.ts`, `plugin-host-api.svelte.ts` (the API it is handed), `crates/atlas-core/src/plugins.rs` |

## Shape

```
atlas-app (crates/atlas-app/)      one window per vault; runs the core in-process
   │
ui/ (Svelte 5 + TypeScript + Vite)      dockview tabs, CodeMirror editor, the block registry
   │   HTTP + WebSocket on 127.0.0.1 — the one transport, also the automation API
crates/atlas-core (Rust, axum)          files, watcher, links, Bases, search, git, PTY, commands, plugins
crates/atlas (Rust)                     the `atlas` CLI: serve, capture, cmd, open, today, mcp, guide
   │
the vault: plain files + `.atlas/` (config, keys, commands, plugins, snippets, workspaces, cache)
```

**PDFium on the phone** (docs/design/DESIGN-pdfium-android.md): `crates/atlas-android/src/pdfium.rs` binds pdfium-binaries' `libpdfium.so` at run time (`libloading`; `scripts/dev/fetch-pdfium.sh` puts the pinned build in `local/pdfium/`, `build-apk.sh` packs it); `org.atlas.capture.Pdfium` and `PdfText` serve every reader (`PageSource` draws pages with it, PdfRenderer when it is missing) and the Books reader's selection, find and links. Its host test runs on the Linux build of the same library.

Beside them: `crates/atlas-capture`, the quick-capture box (a native egui window, docs/guides/CAPTURE.md) whose `complete`, `icons` and `send` modules the phone app shares (`crates/atlas-android`, docs/guides/ANDROID.md). **What a capture carries besides its text** has one shape on both: a list of offers, each on or off (desktop `extras.rs`: `Offer { kind, what, on }`; phone `CaptureActivity.Piece`), found in the background (desktop `context.rs`: the browser page under the box via a KWin script + its history, the clipboard, the last screenshot, the screen via Spectacle; phone: the accessibility service, MediaStore, shares), and on save the pictures go through the one `send::attach` (beside today's log note, embedded under the line). A new kind of thing to carry is a new `Kind` there, not a new path.

## Keys: one list, a few kinds of binding

Every shortcut is a command's `keys` (`ui/src/lib/actions.ts`), overridden per vault in `.atlas/keys.toml`; `bindings()` in `keymap.svelte.ts` is the one list the window's key handler (`App.svelte`, capture phase) walks. Two optional fields on a command:
- `alsoKeys: [...]` — more chords for the same command, not rebindable (the palette: Ctrl+K, also Ctrl+Shift+P and F1; the side panel: Ctrl+Alt+E, also Ctrl+B).
- `where: "note"` — the chord counts only while the keyboard is in a note editor (`.cm-editor.live-cm`, a tab or an embedded one), and there it wins over a command bound to the same chord everywhere. This is how Obsidian's keys live beside the app's: in a note Ctrl+B is bold, Ctrl+I italic, Ctrl+K a link (`note.bold`, `note.italic`, `note.link` → `ui/src/lib/editor/md-format.ts`, reached through `registry.noteFormat` so the commands run at once and `actions.ts` does not import CodeMirror); anywhere else Ctrl+B is the side panel and Ctrl+K the palette. Ctrl+Alt+B and Ctrl+Shift+B were taken (bookmark, build), so the side panel's everywhere key is Ctrl+Alt+E.
- `yieldTo: "<css selector>"` — panes that keep the chord for themselves: the key is left alone when it is typed inside one, or when focus is nowhere and such a pane is the active one (`keeps()` in `App.svelte`). The zoom keys yield to `.pdf-pane`, which zooms its page. `yieldToTerminal` is the older, fixed form of the same idea.
- A chord may name a **character** instead of a key: `Ctrl+Plus`, `Ctrl+Minus` (`CHARS` in `keys.ts`) match the typed `+` / `-` with or without Shift, because those sit on different keys in every layout (all other chords match the physical key).

**Zoom**: Ctrl++ (also Ctrl+=), Ctrl+- and Ctrl+0 zoom **the tab that has the keys** (`ui.zoomIn` / `ui.zoomOut` / `ui.zoomReset` → `zoomPane()` in `lib/pane-zoom.ts`): the app's size variables (`--ui-scale`, `--code-size`, `--prose-size`) are overridden on that tab's own element, so every pane follows without knowing; a terminal reads `paneZoom(id)` for its font. Kept per pane in `.atlas/cache/shell.json`. The PDF keeps the chords for its page zoom (`yieldTo`). Ctrl+Alt with the same keys zooms everything (`ui.zoomAll*` → `zoom()` in `settings.svelte.ts`, which moves the four text sizes of the settings). The first version zoomed everything on Ctrl++; Ctrl++ must magnify only the focused tab.

**VS Code's keys in a code file**: CodeMirror's own keymaps (`defaultKeymap`, `searchKeymap`, `foldKeymap` in `create.ts`) already are VS Code's — Ctrl+/ comment, Alt+↑/↓ move the line, Shift+Alt+↑/↓ copy it, Ctrl+D next occurrence, Ctrl+Alt+↑/↓ add a cursor, Ctrl+Shift+[ / ] fold, Ctrl+Shift+\ matching bracket, Ctrl+] / Ctrl+[ indent. Two were taken by app commands and one was missing: Commands (Ctrl+Shift+K) and Library (Ctrl+Shift+L) now `yieldTo` a code editor (`.cm-editor.code-cm`), so there they are *delete line* and *select all occurrences*; and Ctrl+G is *go to line* in code (`codeExtensions`; "find next" stays on F3). Ctrl+. asks the language server for its code actions (quick fixes, refactorings) and offers them in the palette's chooser (`codeActions` in `lsp.ts`). Test: `ui/tests/code-keys.spec.ts`.

Keys inside the editor that are not commands (Tab, search, vim, the language server's F2 / F12) are CodeMirror keymaps in `ui/src/lib/editor/create.ts` and `lsp.ts`. Test: `ui/tests/note-keys.spec.ts`.

## A pane and its block are two spellings of one thing

`specFromOptions(kind, options)` (`panes.ts`) turns a block's options into the pane it shows, and `embedOptions(spec)` is its reverse: the options that show an open pane as a block. "Open as tab" on an embedded block uses the first; **"Embed in <note>"** in a tab's right-click menu uses the second and writes a ```` ```view ```` block after the caret's paragraph of the note last written in (`embedItem` in `sidebar.svelte.ts`; the editor handle's `insertBlock`). A new pane kind must appear in both switches or it cannot travel between a tab and a note.

## Agent files are kept apart (one predicate)

`Config::is_agent_file(rel)` (`config.rs`, the setting `[editor] index_exclude`) says a file is an AI agent's own — memories, session logs, its instructions — and not one of the user's notes. Everything that gathers "the user's notes" asks it:

| where | how |
|---|---|
| link index: backlinks, graph, Bases, tags (`links.rs`), open tasks (`today.rs`) | `index_excluded` (agent files + the note templates) |
| activity list on Today (`today::recent_changes`) | `is_agent_file` |
| search by text (`rg` globs), by file name — which is also quick open and `[[` completion — and replace across files (`search.rs`) | left out unless `Opts.agent` (`?agent=true`; the Search pane's Claude switch) |
| a link by name in the editor / reading view (`ui/src/lib/vault.ts`) | `isAgentFile` in `ui/src/lib/agent-files.ts`, the same pattern rule in TypeScript: a note's `[[name]]` never lands on an agent file; an explicit path still opens it; agent files resolve among themselves |
| file tree | shows everything |

A new feature that lists or searches notes must go through `walk::files` and one of these — do not walk the vault on your own. Tests: `agent_files_are_searched_only_on_request` (core), `ui/tests/agent-files.spec.ts`.

`walk::PAGES` (`.atlas/pages`) is the one dot-folder the walk enters: the vault's own pages (the starter kit's Inbox, Next, Projects) live there instead of in the vault's root, and links, quick open and embeds must still find them.

## Where a file is read and saved: always here

Every API call of the interface goes to this vault's own core, `apiBase()` in `ui/src/lib/api.ts` (the desktop core, a server vault's prefix such as `/v/phd`, or a server vault reached through the bridge, `/remote/<host>/v/<name>`). There is no per-file routing: a mirrored vault's files are read and written in its own folder, and the core decides at its write functions whether the server must lend the path first (`mirror_guard.rs`, below). The live room of a mirrored vault's note or drawing is spliced to the server's room by the core (`server.rs live_ws`), and only the room's writer saves (`lib/live.ts writes()`). So a pane, a block, an embed or a plugin writes a file with the plain `api.*` call and needs to know nothing about mirrors. What the interface keeps of the mirror (`lib/mirror.ts`): the bridge address (`bridgeBase`), whether the server answers (`reach`, `mirrorState`), its vaults (`serverVaults`), its sign-in (`signInToMirror`), and the `⇄ host` chip of the Editor and Excalidraw panes, which says who writes. Do not add a route or build a URL to `/remote/…` in a pane: a write that should reach the server is the core's business.

## Tables edited in place

`lib/editor/table-edit.ts` hooks into the live preview's `hydrateBlock` (`editor/create.ts`). It acts on the next frame, because the vendored `live-preview.js` draws a block before attaching it, and before the view exists on the first draw. It finds the table's lines from the block's place (`posAtDOM`). A click in a cell edits that cell's markdown, and leaving it rewrites only that table's lines (`tableAt` / `cellsOf` / `linesOf`, pure). Moving to another cell after a change is remembered (`pending`), so the cell opens again once the preview redraws the table. Tables inside embeds and Bases are not touched.

## Bases: editing a view

A view's settings panel is `components/BaseViewEditor.svelte`, opened with the sliders button on a Base's bar. Filter groups are drawn recursively by `BaseFilterGroup.svelte`. Every change goes through one call, `POST /api/base/view` with a `ViewEdit` (core `bases/edit.rs`): `hide` / `show` / `board` / `filters` / `sort` / `order` / `rename` / `duplicate` / `remove`.

How the core handles them:
- **Writing.** The core rewrites only that view in the `.base` YAML.
- **The filter's type.** `api::Filter` is either an expression string or a group (`{and | or | not: [...]}`), exactly as Obsidian writes it. It goes through JSON to and from YAML (`Filter::from_yaml` / `to_yaml`), because serde_yaml writes enums as YAML tags.
- **What a view sends back.** It carries its `filters` and `sort`, so the panel shows what is there.
- **Empty groups.** An empty group lets every note through, so a group just added does not empty the view.
- **Building conditions.** The condition builder writes only expressions the core's evaluator reads (`==`, `!=`, `.contains()`, `>`, `<`, `.isEmpty()`, `.isNotEmpty()`, `file.hasTag()`, `file.inFolder()`).
- **A note's tags** (`file.tags`, `file.hasTag()`), as in Obsidian: its properties' tags as written, then the `#tags` in its text and its PDF marks' tags (the index's, `tags::of_note`), each once.


## Embeds: from an embed to its original

Every mounted embed (`![[note]]`, a PDF, a drawing, a file; `[data-embed-path]`, set by `lib/embeds.ts`) can be left for its original. `lib/embed-open.ts` owns one floating ↗ button for the whole page and places it beside the first line of the embed under the pointer. It is a single button because an embed's own children are redrawn at will. Ctrl/⌘+click anywhere in an embed does the same; it is caught in the capture phase, before CodeMirror would add a second caret. A new kind of embed gets both just by being mounted through `embeds.ts`.

## Writing vault files: vault_write

The core changes files on disk **only** through `crates/atlas-core/src/vault_write.rs`. Pick the family by where the file lives:

| the file | call | why |
|---|---|---|
| anything in a vault that Syncthing carries: notes, pages, drawings, `.atlas/config.toml`, `.atlas/plugins/`, `.atlas/plugin-settings/`, `.atlas/trash/`, `.atlas/pending/`… | `vault_write::write` / `create` / `append` / `rename` / `copy` / `remove_file` / `remove_dir_all` / `mkdir` (`write_with` to stream, `guarded` around an outside program's change) | asks the vault's `WriteGuard` first and tells it the new content's `ContentHash` (SHA-256) after: the mirror's lease |
| per-device state under `.atlas/cache/` (logs, thumbnails, PDF text, `server.json`, work folders) | `vault_write::cache::*` | never synced: no lease; `debug_assert!`s the path is in a cache |
| outside every vault (`~/.config/atlas`, `$XDG_STATE_HOME/atlas`, the secrets store) | `vault_write::outside::*` (`write_private` for 0600) | not a vault's content |

Unsure whether a path under `.atlas/` is synced? It is vault content: only real caches are exempt. Every write takes an absolute path (`ws.resolve(rel)?`, `root.join(…)`); `write` is atomic (a temporary beside the file, renamed in) and makes the parents, so no `create_dir_all` before it.

**The guard**: `ws.set_write_guard(Arc<dyn WriteGuard>)` registers it for the vault's root, process-wide, so every `Workspace` on that root and every function that takes a bare `root: &Path` is covered; `before(rel, kind, current_hash)` may refuse (the write stops untouched), `after(rel, kind, new_hash)` is told. With no guard (the default `NoGuard`) nothing is hashed.

**The rule**: `crates/atlas-core/clippy.toml` disallows `std::fs::write`, `File::create`, `OpenOptions::open`, `rename`, `copy`, `hard_link`, `remove_file`, `remove_dir(_all)`, `create_dir(_all)`; the gate's clippy stage fails on any use outside `vault_write.rs`. Tests may write fixtures freely (`cfg_attr(test, allow(…))` in lib.rs; an `allow` atop each `tests/*.rs`).

**The mirror's guard** (`mirror_guard.rs`) is the one real `WriteGuard`. A local vault with `mirror = …` on the vault list gets a `LeaseGuard<Remote>` when its core starts it or the mirror is set (`install_for_mirror`). It calls `POST <mirror>api/lease/ask|done`, signed in with the bridge's kept cookies, and identifies itself by `device_id()` (`$XDG_STATE_HOME/atlas/device-id`). A server vault gets a `LeaseGuard<Local>` on its own table (`AppState.leases`) once a device first asks (`install_on_server`). What a refusal means to a caller:
- `Error::Conflict` (409): this copy is behind the last version, so a change computed from it would undo another device's. Read the file again.
- An error after ~20 s: another device holds the path, or Syncthing never brought the last version for an append.
- An unreachable server lets the write through (§4).

A new write path needs nothing extra, because it goes through `vault_write` like the rest. To check the whole mirror against real Syncthing (two cores, concurrent writers, a control without leases), run `node scripts/dev/mirror-stress.mjs` ("Under load"). It takes about 1 minute.

## The note index (links.rs): one shared, incremental index per vault

Backlinks, the graph, Bases, tags, `[[` targets, known properties and a move's relinking all read one index: `links::snapshot` / `links::vault` → an `Arc<Index>` (every file in a `Names` resolver, every note's `Arc<Parsed>`: links, properties, tags, size, times). Each call walks the vault and re-reads only the notes whose mtime changed; with nothing changed it hands back the same `Arc` (no copy), an unchanged note keeps its `Arc<Parsed>`, an unchanged file list keeps its `Names`. Paths are stored once in `Names` and looked up by `FileId` (a `u32` newtype). The note's **text is never kept** (unlinked mentions read it again, behind a case-insensitive prefilter); up to three vaults stay warm, one idle for 30 min is dropped. Frontmatter is kept as `note_props::Props` (string keys in file order, one boxed slice; `get` / `iter` / `keys` like a `Mapping`). **The walk is skipped when the vault's watcher vouches for it** (`vault_changes.rs`): the watcher holds a `Feed` and moves the vault's generation on every real change (in notify's callback, not after the 250 ms batch), `vault_write`'s funnel moves it on Atlas's own writes synchronously, and `links.rs` reuses an index whose `Stamp` (read before its walk) is unchanged, for at most 30 s. No stamp is given without a registered watcher, when a folder failed to get its inotify watch, or when the configuration differs from the watcher's — tests and the CLI always walk. A new writer that bypasses `vault_write` must call `vault_changes::touched`, or the index sees its change only through the watcher. Today's per-file caches (`today.rs` `PerFile`) forget files the last walk did not find and vaults idle for 30 min. A new reader takes the snapshot and never clones `Parsed`; anything per-note it needs goes into `Parsed` at parse time. Measure with `cargo run --release -p atlas-core --example index_probe -- <copy of a vault>` (`INDEX_PROBE_DUMP=out.json` writes every reader's answers, to diff two builds).

## The loop

```
bash scripts/dev/dev.sh ~/Notes          # core + Vite; open http://localhost:5173
```
Svelte, TypeScript and CSS edits appear at once. After a Rust edit: `bash scripts/dev/dev.sh ~/Notes restart-core`. Close the installed app on the same vault first (two cores would both run its schedules). Anything that *types into notes* is tried on a copy of the vault.

```
bash scripts/dev/gate.sh                 # scan → rust → clippy → py → ui (types) → build → e2e
bash scripts/dev/gate.sh py              # every Python test: scripts/vault/tests and each plugin's test_*.py (scripts/dev/py-tests.sh)
bash scripts/dev/gate.sh audit           # Obsidian fidelity on a copy of the real notes (minutes)
```
The `build` stage also parses every chunk of `ui/dist` as a module (`scripts/dev/check-bundle.mjs`, acorn): Vite can build a bundle the browser refuses without a word — `import(await x)` became `m(() => import(await x))`, an `await` outside an async function, and every page stayed blank while svelte-check and the build passed.

Read the printed verdict table. A change is done when the gate passes **and** the changed screen has been looked at (a screenshot, both themes) against [UI-STYLE.md](UI-STYLE.md). After any change to the editor, markdown or embeds, also run the `audit` stage and compare with the baseline in [MD-RENDERING.md](MD-RENDERING.md).

## Recipes

### Add a block
```ts
// ui/src/lib/blocks.ts (built-in) — or `atlas.registerBlock` from a plugin, which is usually the right place
registerBlock({
  type: "wordcount", title: "Word count", icon: "file-text",
  mount(host, ctx) {                       // ctx: { src, options, doc, host, setTitle }
    const off = on("fs", (e) => { if (e.paths.includes(ctx.doc)) draw(); });
    const draw = () => api.file(ctx.doc).then((f) => { host.textContent = `${f.text.split(/\s+/).length} words`; });
    draw();
    return off;                            // the cleanup
  },
});
```
It is then usable as `type: wordcount` in a note, `wordcount` in a page or in the sidebar's file, appears in the page's "add a block" chooser, opens as a tab, and can be bookmarked or pinned (`{view: wordcount}`). `ctx.host` says where it is (`note`, `page`, `tab`, `side`). Flags: `height` (it fills a box), `card` (wants a card surface in a page), `file` (it shows a file: the chooser asks which), `tab(ctx)` (what "open as a tab" opens), `options` (its options as form fields — the page's "Options…" is drawn from them; built-ins list theirs in `lib/block-options.ts`; see `docs/guides/PAGES.md`).

### Add a setting
Add a field with a doc comment to the right struct in `crates/atlas-core/src/config.rs` and to its `Default`. The doc comment is the description in Settings; the page and control are generated from the schema (`ui/src/lib/settings-pages.ts` places sections; a new section gets its own page automatically). Run `cargo test -p atlas-core` to regenerate `ui/src/lib/gen/`. Read it in the UI as `settings.config.<section>.<field>`; react with `onSettings`.

### Add a UI command
One entry in `ui/src/lib/actions.ts`: `{ id: "ui.x", title: "…", keys?: "Ctrl+Alt+X", run }`. It is in the palette, bindable in Settings → Keyboard, and listed by `window.__atlas.commands()`. Give it `icon` (and a short `label`) and it can be a toolbar button: a toolbar lists command ids (`SHELL.md`). Commands that come and go with files (one per workspace, one per bookmark) are set with `setCommands(prefix, list)` from `keymap.svelte.ts`.

### Add a kind of new thing (New…)
`lib/new-thing.ts` is the one list behind **New…** (`ui.new`, the phone's +): a blank note and each template (named through `notes-system.ts` `nameAndCreate`, placed by the core: `create_in:`, beside the note in use, `[notes] dir`), a drawing (`draw-new.ts`), and the kinds plugins add (`atlas.registerNew` → `addNewKind`). A built-in kind is a row in `newThing()`'s list; anything vault- or service-specific is a plugin's `registerNew`, never a row here.

### Add a route
1. The types in `api.rs` (or the feature's module) with `#[derive(Serialize, Deserialize, TS)] #[ts(export)]`.
2. The logic as a plain function in the feature's module, with tests beside it.
3. A thin handler + `.route(...)` in `server.rs`.
4. `cargo test -p atlas-core` (regenerates the TypeScript types), then a method on `api` in `ui/src/lib/api.ts`.

### Change what the interface needs from the server
The phone app shows **its own** interface for a vault on a server (`atlas_core::server::ui_file`, served by `AtlasActivity.ownUi`), so an interface may meet an older or newer server. When the interface starts relying on a route or an answer field that an older server lacks, bump `atlas_core::server::API_LEVEL` in the same change: `GET /api/version` reports it and the app warns when the two differ (docs/guides/ANDROID.md, "A server's vault shows the app's own interface").

### Drawings as notebooks
Pages are Excalidraw frames (`ui/src/lib/draw-pages.ts`: `pagesOf`, `pageAt`, `nextPage`, `columns`, `arranged`, `heldView` (page mode: the view held on one page, as `NotepadView.clampToPage`), `frameRef`, `wikiTarget` — pure, tested in `tests/draw-pages.spec.ts`; pages lie in a grid as the Boox Notepad lays them, `Scene.java` `slot`/`nextPage` and `Step.arranged` being the same rules in Java: `per_row` side by side for a new notebook, a drawing with a second row keeps its first row's count, More → "Pages side by side" moves each page and what is on it (its `frameId`) to its slot); the notepad (`Notepad` in `draw-excalidraw.ts`, `NotepadBar.svelte`) and the embeds (`markdown.ts` → `draw-embed.ts` → `sceneSvg(json, dark, page)`) use them; `PaneSpec.excalidraw.page` + `drawingPages` (registry.ts) open a drawing at a page. How a pen stroke is outlined is `draw-ink.ts`, which Excalidraw consults through a build-time rewrite (`vite.config.ts` `inkStroke`, which fails the build when Excalidraw's code moved).

### Add a library (a page of items: references, films, albums)
Never a new page: write a **source** (`ui/src/lib/library.ts`, `LibrarySource`) and let `components/library/Library.svelte`
draw it — search, sort, tabs, groups and tags at the side, a list or covers (`LibraryCover.svelte`: a vault picture, a
`[[name]]` or an address, asked when it nears the view), the selected item with its actions. An action is a `run`, a
`confirm` (asks first) or an `edit` (a form with `save`); a `choice` changes one value in place (a shelf). In the core:
`lib/library-references.ts` (References, `panes/Library.svelte`). From a plugin: `atlas.mountLibrary(host, source)`
(the catalog's `catalog.app`). Tests: `library.spec.ts`, `catalog-library.spec.ts`.
has the why. **Register it** so it is one of the vault's libraries: `registerLibrary({ id, title, icon, by, source })`
(`lib/libraries.svelte.ts`; a plugin: `atlas.registerLibrary(source)`) — the **Libraries** page (`panes/Libraries.svelte`,
pane kind `libraries`, the phone's bottom-bar **Library**) shows those the vault's `[ui] libraries` names, in its
order (none: all). The core's own are Drawings (`lib/library-drawings.ts`: every drawing but a file's ink, its note's
`project`/`topics`/`tags` as the filters, its first page as the cover) and References. Test: `libraries.spec.ts`.

### A plugin as a file's editor (claims, anchors, dirty, save)
A plugin's pane becomes the default view of a file type by `claims = ["*.epub"]` in its manifest (`plugins.rs` lists it apart and adds it to `opens`; `startMain` registers the opener with `claims`). A plain open goes `openPath(path, line, { anchor })` → `resolveSpec(path, line, anchor)` (openers.ts): the vault's `[files] open_with` for the extension, else the first enabled plugin claiming the path, else `specForPath`. A link's `#…` (`openWikilink`) travels as `PaneSpec.plugin.anchor` (not part of the pane's id: one tab per file) to `atlas.anchor`; a later link to an open pane goes through `pluginAnchors` (registry.ts) to the view's `pane.onAnchor`. `Plugin.svelte` gives the view `atlas.pane` (`setDirty`, `onSave`, `onAnchor`): the dirty dot is the core's `setDirty`, Ctrl+S in the pane runs the save hook, and the pane registers its save in `paneParks` (registry.ts) so `closePanel`, the window closing (`App.svelte`), a reload (`ui-reload.ts`) and another workspace (`workspaces.ts`) save it as they park editors — all through `parkOf` / `parkAll`. A plugin switched off registers no opener, so it claims nothing. Test: `ui/tests/plugin-claims.spec.ts`; Rust: `plugins::tests::claims_are_opens_too_and_said`.

### Add a pane kind
Add the variant to `PaneSpec` in `panes.ts`; the type check then lists every switch to extend (`paneId`, `paneTitle`, `paneIcon`, `paneZone`, `specFromOptions`, `KINDS`) and `pane-components.ts`. Write `ui/src/panes/<Name>.svelte` taking `{ spec, panel }`. It becomes a block automatically. Ask first whether it should be a block or a plugin instead: most new things should.

### Add an editor feature
Its own module in `ui/src/lib/editor/` exporting an extension, wired with **one line** in `create.ts` (every file), `note-extensions.ts` (notes) or `code-extensions.ts` (code). Never a second editor: tabs and embedded editors are the same `createEditor`.

Examples, each one module + one line:
- `ansi.ts` `ansiColors()` — ANSI SGR colours in any file that holds `ESC [` in its first 200 k characters (logs, run output, files read over SSH): the codes hidden (shown on the line being edited), the text between them in the terminal palette (`--ansi-*` in `tokens.css`), 256-colour and RGB codes as inline colours; the state carries across lines. Placed before `highlightSpecialChars()` so a hidden ESC is not drawn as a special character. Parser `ansiLine` / `applySgr` are pure. Test: `ansi.spec.ts`.
- `task-tick.ts` `tickTaskLine` — a task box (and Ctrl+L) ticks through the core's `POST /api/task/line`, as Home does (docs/guides/TASKS.md).
- `task-dialog.ts` `editTask` — Obsidian Tasks' "Create or edit task" form (`components/TaskDialog.svelte`) on the caret's line; parsing / writing a task line is `lib/task-line.ts` (MdFormat `taskDialog`).
- `note-extensions.ts` `headingRepeats` — the inline title left out when the first heading says the same.
- The `[[` list comes from the core (`GET /api/link-targets`, `link_targets.rs`); `md-complete.ts` only draws it (preview, new-note row, `#^` block ids). **Ranking** ("not just alphabetical, otherwise all dates just appear first"), smallest sort key first: (1) for an empty or short query (≤ 3 characters) every *dated* note waits below the rest — named by a date stamp (`2026-10-17 Fri`, `2026-W42`, a kept mail `2026-10-16 Re …`) or under `log_dir`; a query starting with a digit is a date search and holds nothing back; (2) the match tier `Exact` (name, alias or title) > `Prefix` > `WordStart` (every query word starts a word of the name; letters after digits count, `qin2022hubbard`) > `Substring` > `Alias` (an alias/title holds the words) > `Path` > `Fuzzy` (letters in order, ≥ 3 letters, tighter first); (3) dated notes after the rest within a tier; (4) usefulness points: recently opened (`.atlas/cache/recent.json`, written by `lib/recent.ts`: 40 for the latest, one less per place), linked from or to the current note (30), notes linking to it (4·log₂(1+n), at most 20), changed lately (15/(1+days/3)), a note +3 over other kinds; (5) the shorter path. An empty query lists only files with ≥ 5 points. One pass over the links per request (`Snapshot::link_stats`: neighbours and incoming counts), ~20 ms on the user's 1300-note vault (debug build). Papers from the Library (`citeMatches`) lead the list only when their citekey or an author starts with the query (at most five); title-word matches follow the core's list. Tests: `link_targets.rs`, `markdown-aids.spec.ts`, `cite.spec.ts`.


### Build a plugin on another plugin

A meta plugin (the catalog) owns a mechanism; its subplugins add to it without code in the core: `requires = ["<id>"]` and a free-form `[contributes.<id>]` table in their `plugin.toml`. The core only (1) refuses to load a plugin whose requirement is missing, broken or off — one predicate, `plugins::blocked` (core: tools) mirrored by `pluginBlocked` (page: main.js, panes, commands), with Settings showing the reason — (2) starts required plugins first, and (3) serves `GET /api/plugins/{id}/contributions` (`plugins::contributions`). Everything else, including the table's shape, belongs to the meta plugin. Tests: `plugins::tests::a_subplugin_contributes_to_its_meta_plugin_only_while_both_can_run`, `ui/tests/plugin-requires.spec.ts`.

### A plugin's own files by URL, and a module shared between plugins
A plugin's modules, fonts, pictures and workers are served by the core at **`<apiBase>/plugin-files/<rev>/<vault path>`** (`crates/atlas-core/src/plugin_files.rs` `locate`, the route `plugin_file_get` in `server.rs`), outside `/api` because `import()`, `@font-face`, `<img>` and `new Worker` cannot send `x-atlas` (the sign-in and the local lock still apply in `guard`, as for `/media/`). Only `.atlas/init.js` and files inside `.atlas/plugins/<id>/` are served: no dot segment below the plugin's folder, no symlink leading out of it (`paths::safe_join` on the canonical folder; the folder itself may be a link), HTML as plain text, `nosniff`, `no-cache` with an ETag (an unchanged file is a 304). The page side is `ui/src/lib/plugin-files.ts`: `pluginFileUrl(path)` and `pluginAssetUrl(id, rel)` (behind `atlas.assetUrl`); `<rev>` is a counter bumped on every `fs` event under `.atlas/plugins/` (a listener made when the module loads, before any pane or plugin start listens), because ES modules are kept by URL for the page's life — a reloaded plugin must get new URLs to run its new code. Since the URL *is* the vault path, `importModule` (`plugins.svelte.ts`) is one `import(url)`: the browser resolves every relative import itself — static, dynamic, `new URL("./x", import.meta.url)`, a worker's — and a sibling plugin's module is `../zip/zip.js`, as on disk. This replaced `blobModule` (each module fetched with `api.file`, its relative static imports rewritten to `blob:` URLs by a regex; no dynamic imports, no `import.meta.url`). The page must be same-origin with its core (it is: the desktop window, a server's page, the phone's WebView, the bridge's `/r/<host>` page); the Vite dev server proxies `/plugin-files` with `/api`; the phone app's WebView passes `/plugin-files/` to the server (`AtlasActivity.ownUi`). The interface's `API_LEVEL` is 2 for it (an older server has no such route). **A shared module** is a library plugin's file (`plugins/beta/zip/zip.js`: no pane, no main.js) that others import by relative path and declare with `requires = ["zip"]` (so Settings says why one is blocked when it is missing) — no bare specifiers, no import map, no source rewriting; the core carries no plugin's library. A library's change reaches its importers at their next reload. Tests: `plugin_files::tests` (types, escapes, links), `server_mode::a_plugins_own_files_by_url_signed_in_and_inside_its_folder` (signed in, `/v/<name>/`, 304, refused paths), `ui/tests/plugin-assets.spec.ts` (static / dynamic / worker imports, a sibling's module, a picture and a font, an edit reloading, a `/v/<name>/` page), `example-books.spec.ts` and `example-manga.spec.ts` (the shared zip reader).

## Conventions that keep it maintainable

- **Make wrong states impossible**: closed unions with exhaustive `switch`, `Record<Kind, …>` tables, typed JSON generated from Rust. Prefer a compile error to a convention.
- **One implementation per idea.** Before adding a mechanism, look for the registry it belongs in (blocks, commands, openers, entity providers, suggestions, settings schema).
- **Single-purpose modules; logic out of components.** Models with pure edit functions (`page-doc.ts`) are testable and reusable; a component draws and wires.
- **Comments say why**, in a line or two. Long reasoning goes in `docs/`.
- **The small helpers exist once**: an error as text is `errText(e)` (`errReason(e)` without the API's "VERB /path: 500 "), HTML escaping `escapeHtml` (`ui/src/lib/text.ts`); a path's folder `dirOf`, its last part `basename` (`ui/src/lib/paths.ts`). A command that rewrites the start of each selected line (to-do, list cycle, heading / quote / list buttons) goes through `rewriteLineStarts(view, pattern, head)` (`ui/src/lib/editor/md-format.ts`). In a Python plugin helper the web is `atlas.fetch` / `fetch_json` (paced, patient with 429s). Grep before writing one.
- **Vault-specific code never enters this repo** (see EXTENDING.md's scope rule).
- **Every new feature**: its settings as `Config` fields, a Playwright spec on the fixture vault (`ui/playwright.config.ts` builds it), a doc line.
- **Big changes get a `docs/REFACTOR-<topic>.md`** (what, why, before/after, what to watch).

## Windows and macOS

Platform differences live in one place, `crates/atlas-core/src/platform/`. Nothing else in the core branches on the OS:
- `dirs.rs` gives the user's folders per OS (`Base::Config`, `State`, `Data`, `Cache`, `Runtime`), with `XDG_*` variables winning everywhere, plus `home()`, `expand_tilde()` and `tilde()`. Never read `$HOME` or `XDG_*` directly.
- `proc.rs` covers processes: `pid_alive`, `own_group` and `stop_group` (a child and its children, ended together), `detach`, `hostname` and `file_id`.
- `open.rs` opens things outside Atlas: `reveal` (the file manager with the item selected) and `url` (the system browser).
- `run_line.rs` turns a `run =` line into a process, with no shell when the line is a program and its arguments. Otherwise it uses `sh -c`, which on Windows means Git's `sh`. `executable()` finds a program file as the shell would, with `.exe` on Windows.

In the desktop app, everything WebKitGTK-only (ad blocking, web tabs, pinch, `window.open` without a click) stays behind `cfg(target_os = "linux")`. The capture box's Wayland input region and D-Bus context are Linux-only too (`region_none.rs` is the stub).

**Windows from Linux**: `bash scripts/dev/windows.sh build | test | run <program> | wine …`. It builds with `cargo-xwin` (`x86_64-pc-windows-msvc`, Microsoft's CRT and SDK in `local/xwin`) and runs under Wine in `local/wine`, never `~/.wine`. Everything goes through `heavy.sh`. The e2e suite runs against the Windows core with `ATLAS_SERVER_CMD="bash scripts/dev/windows.sh run atlas" npx playwright test`. **macOS** cannot be built here (osxcross needs Xcode's SDK): CI's macOS job builds and tests it. CI's steps run through `scripts/dev/ci-annotate.mjs`, which turns a failed step's compile errors, build-script panics, failing tests and end-to-end specs into annotations: `curl https://api.github.com/repos/<owner>/<repo>/check-runs/<job id>/annotations` reads them with no sign-in, where a job's log needs one. Installers come from `cargo tauri build`, configured by `tauri.windows.conf.json` (NSIS; cross-building it needs `makensis`) and `tauri.macos.conf.json` (`.app`, `.dmg`). The plan and what has been checked are in the internal design notes.

## Releasing to the desktop

`bash packaging/install.sh` builds the UI, copies it to `~/.local/share/atlas/ui`, installs `atlas`, `atlas-app` and `atlas-capture` into `~/.cargo/bin`, and the desktop entry (which starts the binary by its full path; an entry that already starts Atlas on a chosen folder keeps its command). Restart Atlas afterwards. Started without a folder, the app opens the most recently opened vault — on the very first start there is none yet, so it opens a small Welcome vault that says how to open yours (Ctrl+Alt+V, type the folder).

**The icon** (the app's, the browser tab's, Android's, KDE's) is drawn once as SVG in `packaging/icon/`; `node scripts/dev/icons.mjs` writes every PNG/ICO/ICNS from it — never edit an icon PNG by hand (guides/ICON.md).

**Kept current by itself:** `bash docs/scripts/auto-install.sh enable` writes a `post-commit` hook that builds and installs **what was committed** in the background after every commit — from a git worktree of its own in `/tmp/atlas-gate/auto-install-src` that shares `node_modules` and cargo's `target/`, never in the working tree (the first version built there, and replaced `ui/dist` under running browser tests: "Failed to fetch dynamically imported module", and a test's start-up timeout) (one build at a time; log `/tmp/atlas-gate/auto-install.log`; `disable` removes the hook). The hook lives in `.git/hooks/`, so it is per clone and not committed.

**target/ size.** cargo never deletes a build it stopped using, and Atlas makes many: every feature set (`cargo test -p X` and `--workspace` unify features differently), profile (dev, test, clippy's check), target triple (the two Android ones), toolchain, `Cargo.lock` change and **source path** (auto-install's worktree in `/tmp`, old worktrees) is a separate copy of every crate built — atlas-core alone ~170 MB a copy, 114 copies in three days. target/ reached 76 GB and filled /home. `scripts/dev/trim-target.sh` (`--dry` to see) keeps, per crate and profile folder, the newest build always and up to 3 more younger than 2 days (`KEEP`, `DAYS`), and removes the rest with their `.fingerprint/`, `build/` and `incremental/` folders; it does nothing while a cargo or rustc runs. The gate runs it after its verdict and auto-install after each install. First run: 45 GB → 14 GB. Dependencies already build without debug info (`[profile.dev.package."*"]`), Atlas's crates with line tables only.

**Heavy jobs run in a scope of their own** (`scripts/dev/heavy.sh`). On this 13 GB laptop a full `cargo test`/`clippy` reached 4.7 GB with the desktop app, a browser and another session running; memory pressure in the terminal's cgroup passed systemd-oomd's 60 % limit and oomd killed **the whole terminal tab** — the Claude session inside it with the build (2026-10-22 12:15). `heavy.sh <command…>` runs the command niced (`nice -n 19 ionice -c3`) in its own `systemd-run --user --scope` with `MemoryMax` 6 G and `MemorySwapMax` 3 G (`HEAVY_MAX`, `HEAVY_SWAP`) and `CARGO_BUILD_JOBS` 6: over the cap the kernel kills a rustc inside that scope, the build fails loudly (exit 137 / `signal: 9`), and the terminal lives. No `MemoryHigh`: it throttled a test process to a standstill instead of failing it. `gate.sh` and `packaging/install.sh` re-exec themselves through it (`ATLAS_HEAVY` marks being inside, so nested calls only nice); **an ad-hoc cargo from an agent goes through it too**: `bash scripts/dev/heavy.sh cargo test -p atlas-core`. Without a user systemd (a container) it only nices.

**What an open window does with a new build**:
- **Interface changes reload by themselves.** The desktop app serves the UI from `~/.local/share/atlas/ui` (it sets `ATLAS_UI_DIR`; `crates/atlas-core/src/ui_files.rs`), not from the copy built into the program. The page asks `GET /api/ui/build` every 15 s (`ui/src/lib/ui-reload.ts`); when the installed UI changed it saves every open editor (`flush()`) and reloads — the layout is a file, so the tabs come back. `atlas serve` and the tests keep the built-in UI: they test what was built, not what is installed.
- **Core (Rust) changes need a restart.** The app checks its own program file every 20 s and says "Atlas was updated — restart to use it" (`watch_for_update` in `crates/atlas-app/src/main.rs`).
- **While working on the UI**: the **Atlas (dev)** menu entry (`ATLAS_DEV=1`) starts the window on this repository's Vite dev server — every saved `.svelte` / `.ts` / `.css` shows at once (hot reload), with the installed core. `ATLAS_REPO` (written by install.sh) names the repository, since auto-install builds from a temporary copy. Vite binds `127.0.0.1` (`localhost` resolved to `::1` only, and the window never saw it start).

**Checking on the real vault (read-only, WebKit).** Playwright's suite runs on a throwaway workspace in Chromium; the desktop window is WebKitGTK on a real vault. `scripts/dev/webkit-probe.mjs` closes that gap without risk: it opens the **running** Atlas (the port from `<vault>/.atlas/cache/server.json`, or `ATLAS_VAULT` / `ATLAS_URL`) in Playwright's WebKit, lets API GETs through, answers every write with `{}` and closes the event socket — nothing it does reaches the vault. `--dist ui/dist` serves a build that is not installed yet (the fix being checked); a script `export default async ({ page, errs }) => …` does the steps; `--shot` saves a screenshot. `readOnlyPage()` is exported for longer probes. It found this way what the tests did not: the task list never showing on a real vault, `@` listing citation keys, the Home capture list clipped by its block (`elementFromPoint`), the drag offset of the tab list, the Super+C slot. Page errors about `x of f.list` / `messages.length` come from the writes it answers with `{}` and are not the app's. **WebKit on Fedora:** Playwright's WebKit build needs Ubuntu's `libicu74`, `libjpeg-turbo8` and `libbacktrace0` (extract the `.deb`s into `~/.cache/atlas-webkit-libs/lib`) and `libjxl.so.0.8` (a link to Fedora's `/lib64/libjxl.so.0.11`), all copied into `~/.cache/ms-playwright/webkit-<n>/minibrowser-{wpe,gtk}/lib/`; run with `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1`. **A locked core** (the desktop's default): the probe reads its key from `$XDG_RUNTIME_DIR/atlas/server-<port>.key` (as the CLI) and sends it as `x-atlas-token` and the `atlas_local` cookie; without it the page is only the lock screen. **Old layouts:** `migrateLayout` (dock.ts) rewrites a saved layout's retired panes before Dockview reads it (the References pane `library` → the Library page `libraries`); a pane kind retired later gets its line there.

**Native windows without the user's screen.** `scripts/dev/capture/look.sh` (the quick-capture box) and `scripts/dev/signin-look.sh` (the desktop app's sign-in window) start a `kwin_wayland --virtual` on a private D-Bus with their own runtime and config folders, run the binary there, and take screenshots through KWin's screenshot API (and type through the nested Xwayland with XTEST for `look.sh keys`). Keep `ATLAS_LOOK_DIR` short (`/tmp/claude-1000/...`): D-Bus refuses a socket path that is too long. A nested KWin that outlives its script is stopped by PID, never with a `pkill -f` pattern (it would match the shell running it).

**Server mode** (docs/guides/SERVER.md). `serve_on(root, Listen::Server { addr, auth })` instead of `serve(root, port)`: the guard becomes `guard_server` — every request is identified by `auth::Auth` (a session cookie from `/login`, a trusted proxy's `Remote-User`, a bearer device token whose scope must reach the path) or gets the sign-in page / 401; the local `atlas` CLI uses a per-run key in `$XDG_RUNTIME_DIR`. Nothing of it lives in the vault (`~/.config/atlas/server.toml`, `~/.local/state/atlas/server.json`). A new API route a phone's capture token must reach goes into `auth::CAPTURE_PATHS`; everything else is reachable only by the owner and `full` tokens. Unit tests in `auth.rs`, end to end in `crates/atlas-core/tests/server_mode.rs`.

**The local lock** (`local_lock.rs`). `Listen::Local(port, Lock)`: `Lock::Open` is the old desktop guard (Host + `x-atlas: 1`, which stops web pages but not programs); `Lock::Locked` gives the run a key (written owner-only to `auth::local_key_file(port)`, where the CLI and `atlas mcp` already read it) and `guard` refuses anything without it — `Authorization: Bearer`, `x-atlas-token`, or the HttpOnly `atlas_local` cookie that a one-time link `/?k=<code>` sets (`ServerHandle::open_url`, `POST /api/local/link`). A helper's in-process call (`Caller`) passes before the lock. The phone's in-app core is always locked (every app reaches 127.0.0.1); the desktop with `ATLAS_LOCAL_LOCK=1` (`Lock::from_env`, `ATLAS_LOCAL_KEY` fixes the key); **the e2e suite runs locked** (playwright.config.ts: the key as a cookie and a header), so a new client path that forgets the credential fails there. Tests: `local_lock.rs`, `tests/local_lock.rs`, `ui/tests/local-lock.spec.ts`, `atlas-android` `serve.rs`.

**AI agents on a locked core** (`agents.rs`, Settings → AI agents). Each agent `atlas mcp` serves gets a named token of its own (`Agents::allow`), kept as a hash in `$XDG_STATE_HOME/atlas/agents.json` (`ATLAS_AGENTS_FILE`; per machine, every vault) and read afresh on each check, so a revoke reaches every core of the machine at its next request. A request marked `x-atlas-client: mcp` is admitted by a locked core **only** with an agent's token, never with the machine's key; an agent's token may not reach `/api/agents` (no agent allows agents). `atlas mcp` sends `ATLAS_AGENT_TOKEN` (put in the agent's MCP config by the command Settings shows once), and stops with the core's words when the core turns it away (`Server::reach` → `Reach::Refused`) instead of falling back to the files. On a server, agents use device tokens and the `mcp` switch (Settings → Server); `/api/agents` answers 400 there. **Agent terminals** (a terminal preset that runs an agent, today `PtyPreset::Claude`) get `ATLAS_AGENT_TOKEN` from `Agents::terminal_token()`: one shared agent, `TERMINAL_AGENT`, made on first use, rotated by a revoke, off by the Settings switch (`PUT /api/agents/terminals`); a new agent preset must call it too. **The desktop app is locked by default** (`Lock::desktop()`, `ATLAS_LOCAL_LOCK=0` opens it); every window it opens on its own core comes in through a one-time link (`open_url`, `POST /api/local/link`). Tests: `agents.rs`, `tests/agents.rs`, `ui/tests/settings-agents.spec.ts`.

**A phone's Back** (`ui/src/lib/back.ts`). Anything that opens over the page — a dialog, a menu, a dropdown, the palette, a sheet, a sub-page like a Settings area — registers how it closes while it is open: `$effect(() => closable(onclose))` (or `$effect(() => { if (open) return closable(() => (open = false)); })`). `dismiss()` closes the newest; the phone app's system Back calls it first (`atlasShell.dismiss()`, AtlasActivity), and in a phone's browser `attachBrowserBack` keeps one guard history entry so the system Back closes, then steps back a place (`navigate(-1)`), then leaves. A new overlay that forgets to register is left open under a Back. Spec `phone-back.spec.ts`.

**Browsing windows and ad blocking**. A web link (`on_new_window` in `crates/atlas-app/src/main.rs`, when `[web] open_links = "window"`) opens in a window of its own (`crates/atlas-app/src/browser.rs`; `atlas-app --browse <url> [vault]` opens one directly, for checks). Ads and trackers are blocked by WebKit's content blocker: `crates/atlas-app/src/web_filters.rs` (the desktop app's own since: the core, which the phone and the server build, no longer carries `adblock`) fetches the lists (EasyList, EasyPrivacy, uBlock Origin's; kept a week in `~/.cache/atlas/web-filters/`) and converts them with Brave's `adblock` crate; the window compiles the JSON through WebKitGTK's C API (`webkit2gtk-sys`, the Rust bindings stop short) and keeps the compile under the lists' hash, so unchanged lists are neither converted nor compiled again. Measured with the real lists: 137,765 rules, 14 MB; debug build 4 s to convert, WebKit 8–9 s to compile the first time, both off the main thread (a window opened before is reloaded once they are ready). Checked in a hidden KWin with a page holding `#ad_banner` and `.sponsored-ad`: shown before the rules, hidden after, the content left alone.

**Rendering and idle CPU.** `ui.gpu_rendering = auto` means *compatible* (no DMA-BUF) on every machine since 2026-10-14: with WebKit's DMA-BUF renderer the window's main thread composited frames nobody asked for — 14–41 % of a core while idle, measured per thread; a CPU profile of the page showed no JavaScript running — and without it idle is 0 % and ~50 MB less. *Accelerated* stays a choice (smoother scrolling). How it was measured: PSS and CPU ticks of the process tree over 10 s idle, and per-thread ticks from `/proc/<pid>/task/*/stat` ( log, 2026-10-14). Tauri 3's CEF (Chromium) back-end was tried the same way: 642 MB and 116 % of a core idle (an upstream bug) — not worth it.

**A right-click menu** is one component, `ui/src/components/ContextMenu.svelte`: give it `x`, `y`, `items` and `onclose`. An item is `{ label, run, detail?, hint?, icon?, danger?, disabled? }` (`detail`: a faint second line saying what the row does) or `"sep"`; `hint` is the shortcut shown at the right (use `keysOf("command.id")`), `icon` any `IconName`. The component does the rest: the first row has the keys at once, arrows / Home / End move (wrapping), a letter jumps to the next row starting with it, Enter runs, Esc / Tab / a click outside / the window losing focus closes; it is placed from its measured size and flips above or left of the pointer rather than leave the window. Never write another menu; add a row. Test: `ui/tests/context-menu.spec.ts`. Its owner keeps a `MenuAt | null` (`ui/src/lib/menu.ts`) and opens it with `atPointer(e, items)` (a right-click) or `below(e, items, gap?)` (a button's menu, under the button) — never a hand-made `{ x, y, items }`.

**Shared looks and formatters, not copies**: the primary button is `<button class="btn primary">`, styled once in `ui/src/styles/base.css` (`button.btn.primary`, which outranks a component's scoped `.btn`); a settings panel's section `<h3>` gets its look from `SettingsPage.svelte` (`.page :global(h3)`) and keeps only its own margin; a file size and a short file time are `bytes()` and `shortWhen()` of `ui/src/lib/text.ts`. **The editor's right-click menu** is `ui/src/lib/editor/menu.ts` (one line in `create.ts`: `editorMenu({ markdown, onOpenLink })`). The function `items(view, target, o)` builds the list: "Open link" when a wikilink is under the pointer, then Cut / Copy / Paste / Select all, then the note keys (Bold, Italic, Link, To-do — `formatNote(view, kind)` of `md-format.ts`, the same code as the keys) or, in a code file with a language server, definition / references / rename / format. To add an entry, add a row there. Plugins add theirs through `pluginMenu("editor", …)` at the end of the list (`lib/plugin-menus.ts`; the tab, file and block menus end the same way). Three rules it keeps: a right-click outside the selection moves the caret there first; Shift+right-click leaves the browser's own menu (spelling suggestions live there); a click on a rendered block (`contenteditable="false"`: a table, a terminal, a picture, a formula value) is not taken, so that block's own menu or the browser's shows. Paste reads the clipboard through `navigator.clipboard.readText()`; where the window refuses, a toast says to use Ctrl+V — **not checked in the desktop window (WebKitGTK) yet**. Test: `editor-menu.spec.ts`.

**Looking at the real vault in the other theme, without touching it:** `node scripts/dev/theme-shots.mjs light /tmp/shots` (the dev server must be running). It opens the main panes one after another through the palette and saves a screenshot of each. Add a pane by adding a line to `PANES` in the script. Use it for every visible change ("judge from a screenshot, in both themes").

**A file the app both reads and writes must not echo.** `bookmarks.svelte.ts` keeps the file's text as it last read or wrote it (`known`): the same text coming back from disk is not news, and a save whose text is the same is not made — and does not republish. Without the second half, a watcher that saves on every publish loops for ever with identical writes (it did, 2026-10-14, at several writes a second; `pins-quiet.spec.ts`). Any new "the shell is a file" module follows the same rule.

**What the core does for plugins** is a few small modules, each with its tests: `plugins.rs` (the manifest: permissions, versions, the plugin list), `plugin_files.rs` (a plugin's own files by URL), `plugin_settings.rs` (the settings schema — kinds, `when`, `group`, lists of records — defaults, and what saving writes with `toml_edit`), `plugin_net.rs` (`fetch`: the host list, redirects, the secret in a header), `service_signin.rs` (a gate in front of a service recognised by its answer, the kept sign-in sent with the request; the desktop's `door_window` in `crates/atlas-app`), `secrets.rs` (the store outside the vault), `helper.rs` (the long-lived process: JSON lines, restart, the crash limit). **Marks for what differs from git** (`ui/src/lib/editor/git-gutter.ts`; `[editor] git_gutter`, on; code files only): a 3 px gutter beside the line numbers — green for a new line, the accent colour for a changed one, a red tick where lines were removed. `changedLines(patch)` (`patch-lines.ts`, no imports, unit-tested) reads the unified diff of the saved file against the index (`GET /api/git/diff`) into a map of line → kind; the marks are a `RangeSet` in a state field, so they follow the text while it is edited, and `refreshGitGutter(view, path)` asks git again when the file is loaded and after every save (`Editor.svelte`). A file git does not know gets no marks (every line would be new); a vault that is not a repository gets none either. Not there: blame, and reverting a hunk from the gutter. Test: `git-gutter.spec.ts`. Looked at in the dark theme only.

**The bar above a code file** (`ui/src/components/CodeBar.svelte`; `[editor] code_bar`, on by default; notes have the formatting bar instead): Find, Replace, Line…, Format, and the file's problems as a count that opens the list — each the same command as its key (`codeTools` in `create.ts` is the one place that names them), so a button can never do something a key does not. **The formula under the caret** (`ui/src/lib/editor/math-preview.ts`, one line in `create.ts`, notes only; `[editor] math_preview`, on by default): a CodeMirror tooltip field. `formulaAt(state)` finds the formula the caret is in — an `InlineMath` or `BlockMath` node of the grammar, or, for an inline formula whose closing `$` is not typed yet, the text after the last unpaired `$` of the line — and `draw` renders it with the same `renderMathInto` as everything else (so macros and the MathJax habits of `math.ts` apply). The renderer does not throw on a formula it cannot read (it draws the source in red, the reason in its `title`): the box then keeps the last good drawing, dimmed, with the reason under it, so it does not flicker between keystrokes. For a display block the box sits under the block's last line. Test: `math-preview.spec.ts`.

**Wikilinks in a terminal** (`ui/src/lib/terminal-text.ts`, `terminal-wikilinks.ts`, one line in `panes/Terminal.svelte`; `[terminal] wikilinks`, on by default). Asked 2026-10-21, from an agent running in an Atlas terminal: the terminal reads `[[…]]` as wikilinks. An xterm link provider (`term.registerLinkProvider(wikilinkProvider(term))`) beside the `WebLinksAddon`. For the row under the pointer, `runAround` reads a **run**: the row with the rows it soft-wraps into (`isWrapped`, up to 40 up and down), each character keeping its cell (wide characters, combining marks); then, only while a `[[` is left open at the run's end (or a `]]` closes one at its start), up to 3 more rows across a *program's own* line break — Claude Code (Ink) wraps its answers itself, so its rows are not `isWrapped`. Those rows are joined by a space with their indentation trimmed; `linksOn` scans the run with `wikilinksIn` and, when a target cut by such a break does not resolve with the space, tries it without (a long word broken mid-word). Resolution is `resolveLink(target, "")`: the terminal sits at the vault's root, so a link resolves as from a note at the root (by path, then by name, shortest path; agent files are not targets, as from any note). A plain click opens it through `openWikilink` (the editor's opener: `#heading`, `#^block`, a PDF's `#page=`, tabs and back/forward the same), Ctrl/Cmd+click beside — the plain click matches the terminal's web links. The pointer on a link asks the window's hover card (`previewAt(target, rect, within)` of `preview.ts`, the card links in notes use; `[editor] link_preview` turns both off) with the resolved path as its heading; a link to no file yet still opens (an empty new note at the root, as the editor's unresolved links create theirs) and its card says *Not in the vault yet* in the editor's unresolved colour (`.preview-missing`) — xterm draws every link with the same underline, so the card is where resolved and unresolved differ. Limits: a hard-wrapped link more than 3 rows long, or a break inside the `[[` / `]]` pair itself, is not found; the underline of a link joined across a program's break also runs under the indentation between its rows (xterm ranges are contiguous). Test: `terminal-wikilinks.spec.ts` (the run reader on a fake buffer; in a real terminal: card, path, missing note, a soft-wrapped link, click opens).

**A block's lifetime** (`hydrateBlocks`, `ui/src/lib/blocks.ts`). Whoever hydrates a piece of rendered markdown unmounts its blocks: `hydrateBlocks(root, doc)` returns the undo for what it mounted (`hydrateFences` hands each fence's to `track`), and an undo clears the `data-mounted` / `data-fence` marker so a later hydrate draws it again. The editor calls it from the widget's `destroy` (the vendored live preview's `releaseBlock` option, beside `hydrateBlock`; CodeMirror calls `destroy` when the DOM goes for good, the view's own destroy included), `Markdown.svelte` from its effect's cleanup. Never by `isConnected`: a hidden tab's DOM is detached (dockview's `onlyWhenVisible`, `dock.ts`) and must come back drawn — a 4-second sweep on it left the views of every hidden note blank until their source was shown. Spec `view-blocks.spec.ts`.

**Where a file was left** (`ui/src/lib/editor/places.ts`). `createEditor` restores the caret and the top line of a file opened with no line of its own, and keeps them on scroll / caret moves (500 ms) and on destroy. Per device (localStorage `atlas.places.v1`, one origin per vault), the last 400 files; a link's heading or a search hit still goes where it says. Spec `note-places.spec.ts`.

**One thing, one row** (`companion::stands_for`, core). A file and its companion note are one thing: a satellite stands for its thing (`thing_of`: ink, a hidden note, a mail's attachment), a file with a shown note (a book, a manga series' entry note) for the note, a file whose note is hidden (a PDF's) for itself. Search (`thing_of`), Activity (`today.rs` `per_thing`) and `[[` completion (`link_targets::one_per_thing`) list each thing once by it; a new list of vault files does the same.

**A new setting must be put on a page by hand**: a Settings page lists its fields by name (`ui/src/lib/settings-pages.ts`, `fields: [...]`, or a whole section with `notes.*`). A field in the schema that no page names exists in `config.toml` but cannot be found in Settings — five of them were in that state for a while on 2026-10-14. Add the name to the page where it belongs, in the same change.

**The gate's first stage is a scan** (`scripts/dev/scan-personal.sh`, also `gate.sh scan`): in the files git tracks outside `docs/`, it looks for a home folder by name (`/home/<name>`), an e-mail address that is somebody's, and anything shaped like a key or a token. A finding fails the gate with `file:line`. A line that must stay carries `scan:allow` and a reason; placeholder addresses (`example.org`, `noreply@…`) are not findings. So a personal path or a pasted token cannot be committed unnoticed — what "this could at some point be published" needs. A test that wants the user's real files takes their place from the environment (`ATLAS_TEST_PAPERS`, `ATLAS_TEST_VAULT`) and skips, saying why, when it is not there.

**A new hook for plugins** follows four rules, all visible in `lib/plugin-menus.ts` (the smallest one): the plugin's function is kept in a module-level list with its plugin id; the app reads the list at the moment of use (no rebuild when a plugin comes or goes); the function is only ever called through `guard(pluginId, where, fn, fallback)` of `lib/plugin-log.svelte.ts`; and the registration returns its undo, which `own(p.id, …)` in `plugins.svelte.ts` runs on reload and switch-off. What the plugin receives is a plain object of Atlas's own making, never a library's type — except the one marked escape hatch (`atlas.editor.extension`).

**A plugin pane opened on something** (`atlas.openView(arg)`): the `plugin` pane spec has an optional `arg` string beside `path`; `paneId` makes it part of the id (`plugin:<id>#<arg>`), so every value is its own tab, and `Plugin.svelte` hands it to the view as `atlas.arg`. One field, no new pane kind: the SSH plugin's Files pane (one tab per host) and its read-only remote files use it. Tests: `example-sftp.spec.ts`.

**Tests never change the process's environment.** Rust tests of one crate share a process and run in parallel: a test that replaced `PATH` for a moment made `git` vanish for the git tests (once, 2026-10-13: `git: No such file or directory`). Pass the value in instead — `detect::claude_on(path)` takes the search path as a parameter.
