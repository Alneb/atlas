# Calendar — the DAV plugin

A calendar plugin written in Rust that puts important dates into a CalDAV calendar on your own server (with app-password support; developed against RustiCal) (2026-10-21). Then (2026-10-23): integrated with the Email plugin, a powerful calendar view inside the app, subscriptions to open iCal calendars, and times shown in local time. The calendar lives in this plugin: **the DAV plugin grown into a Calendar plugin**.

Then (2026-10-23, a review of the first version): it was poorly integrated with the other plugins — one remote server only, settings hard to use, writing to a single calendar only, and the plugin reading mail for tasks instead of Email (and agents, through the MCP) calling the calendar's API — hence **1.1**: several accounts, any calendar written to, no mail read, settings in groups ([REFACTOR-calendar-accounts.md](../../../docs/refactor/REFACTOR-calendar-accounts.md)).

The plugin's **id stays `dav`** (its tools are `dav_*`, its settings file `.atlas/plugin-settings/dav.toml`). Its title is **Calendar**. **Accounts are cards** (Settings → Plugins & automation → Calendar → Accounts, `[[accounts]]` in the settings file): each a name, a server address, a user name, an app password (the secret `accounts.<name>.password`) and an optional colour; calendars (CalDAV) and contacts (CardDAV) come from every account. The design study is [DESIGN-calendar.md](../../../docs/design/DESIGN-calendar.md); the rebuild and what to watch, [REFACTOR-calendar.md](../../../docs/refactor/REFACTOR-calendar.md) and [REFACTOR-calendar-accounts.md](../../../docs/refactor/REFACTOR-calendar-accounts.md).

## Calendars and their ids

A CalDAV calendar's id is **`<account>/<calendar>`** — the card's name and the last part of the calendar's address (`home/personal`, `uni/work`); when two calendars of one account end the same, the whole path. Subscriptions are `sub:<name>`. The ids are what the pane keeps (hidden calendars, colours), what Settings' **New events go to** holds, and what Claude passes as `calendar` (`dav_calendars` lists them). Anywhere a calendar is named, the engine also takes its address, `account/Name`, or a name only one calendar has (two calendars called "Personal" in two accounts: the error lists both ids).

## What it does

- **The Calendar pane** (rail button, "Calendar: open"): month, week, work week, day, agenda and year; the all-day lane, the now-line, overlapping events side by side; drag on the grid to create, drag an event to move it (across days too), drag its lower edge to resize — 15-minute steps, Esc cancels; a click shows the event's card (when, where, calendar, who is invited, the note it came from), `e` the full editor (title, all-day, start / end, repeat, place, description, calendar).
- **Writing to any calendar**: the editor, the new-event card (a click or a drag on the grid) and quick add each have a calendar box offering every writable calendar of every account, grouped by account, the chosen one's colour beside it. It starts on the calendar used last (kept per device), else Settings' *New events go to*, else the first account's first writable calendar. Changing an event's calendar in the editor moves it — to another calendar of the same account or of another one: written there first, then removed here (if the removal fails the new copy is taken back, never two), with Undo. A repeating event asks "this event / this and following / all events". Every change shows at once and is written behind, with **Undo** in the toast; a refusal rolls back with the server's reason. **Times are the user's local time on the 24-hour clock** (the setting `time_format = "12h"` for AM/PM): the engine expands every event in the zone the page gives it, the grid's hours read 00–23.
- **Keys** (Google Calendar's): `d` `w` `x` `m` `a` `y` (or 1–6) the views, `t` today, `j`/`n`/→ and `k`/`p`/← next / previous, `g` go to a date (typed in words), `c` new event, `q` quick add, `e`/Enter edit, Delete / ⌫ / `#` delete, `/` search, `r` sync now, `s` the side panel, `?` the key sheet, Ctrl+K every command. One list (`ui/src/keys.ts`) feeds the keys, the palette and the sheet.
- **Quick add** (`q`): a line in English, Spanish or French — "lunch with Ana tomorrow 13:00", "examen el 15 de noviembre", "réunion lundi à 10h pendant 2h @ D3", "gym cada lunes 7:00" — previewed as you type with what the engine understood (`engine/src/quick.rs`).
- **The side panel**: Create, a mini month (the range on screen marked, busy days dotted), **one heading per account** (in Settings' order; a red `!` with the reason when its last sync failed) with its calendars under it, each with a colour box (a click hides or shows one: `hidden` in Settings, by id; the colour menu writes `colors`, by id; a calendar with no colour of its own takes its account card's), the subscriptions, and — only when *Show important notes* is on — **Important notes**, the vault's notes marked `important: true` with `due:` / `event:` as a calendar of their own (never mail notes); a click on one opens the note.
- **Narrow panes**: under 900 px the side panel folds, under 980 px the view buttons become a menu, under 700 px (a phone) one column: the week shows as the day, the month as the agenda, a round + makes an event.
- **ICS subscriptions** (Settings → Calendar → Subscriptions; `https://` or `webcal://`): read-only calendars fetched again every N minutes, only when changed (ETag / Last-Modified). A card's **Test** reads it once and says how many events it has.
- **Accounts in Settings** (plugin API 12, Settings v2: the cards appear under Settings → Accounts as *Calendar* accounts with a summary `{user} · {url}`, RustiCal and Nextcloud presets, their state and Test; a drawn **Calendars** section lists every calendar with its visibility and colour; the pane's `hidden` / `colors` never show in the form, the tuning fields fold under Advanced): each card has **Test** (it saves the form, then lists the account's calendars or says why not: "app password rejected…", "cannot reach host…"); under the cards, **Sync now**. For the Settings page being redesigned (`docs/design/DESIGN-plugin-settings-v2.md`) the engine answers `account_status` → `{ "<card name>": { state: "ok" | "warn" | "error" | "busy", text } }` ("3 calendars · synced 2 min ago", "app password rejected: …", "no app password yet", "syncing…") and `test_account { record }` → `{ ok, text }` for a card not saved yet (its typed password, else the kept one).
- **No mail is read.** Invitations reach the Calendar only when Email calls `import_invite`; the 1.0 scan of the vault's `mail` folder for `.ics` files and important mail notes is gone. **Important notes** are opt-in twice over: *Show important notes* (the pane, default off) and *Put important notes on the server* (`push_notes`, default off: then `[[tool]] sync`, `on = "fs"`, writes a changed note's `due:` / `event:` to the default calendar, each a narrated line in the plugin's log `.atlas/cache/plugins/dav.log` and a notice in the window). Both read notes only: a note with a `message_id` or `type: email` (Email's) is skipped.
- **The Home card**: ` ```view ` / `type: dav.upcoming` / `days: 7` — today, tomorrow and the rest of the week as a compact agenda, from the cache; a click opens that day in the pane (or the note an event came from).
- **In any calendar view** (the core's generic plugin source): ` ```view ` / `type: calendar` / `from: plugin:dav/events` / `args: {from: 2026-10-01, to: 2026-12-31}`. Each event sits on its day beside the vault's own tasks and notes, and one made from a note opens that note. Since the Calendar, `events` expands repeats and spans every visible calendar and subscription.
- **For Email** (tools Email calls through `POST /api/plugins/dav/tools/<name>`, and agents through `atlas mcp`): `import_invite`, `invite_status`, `contacts`, `agenda` (below).
- **Agents** (`atlas mcp`): `dav_calendars` (every account's calendars with their ids, the default, each account's state), `dav_events {from?, to?, calendar?}`, `dav_agenda {days?}`, `dav_add_event {title, start, end?, all_day?, description?, location?, source, key?, uid?, calendar?}` (any account's calendar by id; answers the id it went to), `dav_remove_event {uid, calendar?}` (finds the calendar it is in), `dav_import_invite {…, calendar?}`, `dav_invite_status`, `dav_contacts {q?, limit?}`, `dav_sync {paths?}`. Free-text dates ("the report is due next Friday") are **not** looked for by the plugin: Claude reads them and calls `dav_add_event` with the mail's Message-ID or the note's path as `source`. The tools take every secret of the plugin (`secrets = ["*"]`: each account's password).

## The contract with Email

| Tool | Input | Answer |
|---|---|---|
| `import_invite` | `{ ics, source, partstat?, attendee?, calendar? }` — the invitation's text, the mail's Message-ID, `ACCEPTED` / `TENTATIVE` / `DECLINED`, the user's address as invited, a calendar id | `{ uid, calendar (its id), status: "added" \| "updated" \| "unchanged", start, end }` |
| `invite_status` | `{ ics }` | `{ uid, in_calendar, partstat?, start, end, conflicts: [{ summary, start, end, calendar }] }` |
| `contacts` | `{ q?, limit? }` (20) | `[{ name, emails: [string], org? }]` |
| `agenda` | `{ days? }` (1) | `{ from, to, tz, events: [{ day, time ("10:00" / "all day"), line ("10:00 Group meeting"), uid, summary, start, end, all_day, location?, calendar_name, color?, … }] }` |

- `import_invite` files the invitation's events in `calendar` or the default calendar for new events (or updates the copy already in any calendar of any account, If-Match on its ETag, with that account's client): `METHOD` dropped, the user's `PARTSTAT` on their `ATTENDEE` line (RSVP taken off), `X-ATLAS-SOURCE` the Message-ID, `X-ATLAS-ME` the user's address. The same answer again is `unchanged` (compared without DTSTAMP / LAST-MODIFIED). A `METHOD:CANCEL` marks the calendar's copy `STATUS:CANCELLED` (`updated`), or does nothing when there is none (`unchanged`). A `REPLY` is refused with the reason.
- `invite_status` reads the cache (one pull first when the cache is empty). The user's answer comes from the calendar's copy: its `X-ATLAS-ME` names the user (so `{ ics }` alone is enough once the invitation was filed), else the `attendee` given, else the first account whose user name is an address. Conflicts: the visible calendars' events overlapping the invitation's first occurrence, not free (TRANSP) and not cancelled, timed with timed and all-day with all-day.
- Times are the user's: `2026-11-04T10:00:00-05:00`, or `2026-11-04` for a day (end exclusive). The zone is the call's `tz` (the page's), else `$TZ`, else `/etc/localtime`.
- `contacts`: the CardDAV address books found from every account (addressbook-home-set through the principal, `/.well-known/carddav`, or the CalDAV address with `caldav` read as `carddav` — RustiCal's layout), cached and refreshed every 6 hours behind the answer; the same person in two books is one contact.

## Important notes (opt-in; never mail)

Deterministic, nothing guessed. Read only when *Show important notes* (the pane) or *Put important notes on the server* (`push_notes`) is on, only in *Only notes in these folders* (`folders`; empty: the whole vault, hidden folders skipped), and **never a mail note** (`message_id` or `type: email`: Email's). Calendar files (`.ics`) are never looked for: an invitation reaches the calendar through Email's `import_invite`.

1. **Important notes**: a note with `important: true` (also `yes`) and one of
   - `due: 2026-11-15` → an all-day event "Due: <title>" (`due: 2026-11-15 17:00` → at that time, an hour long);
   - `event: 2026-12-01 10:00` (+ optional `event_end: 2026-12-01 12:30`; for days, `event_end` is the last day, inclusive) → an event "<title>";
   - `location:` is used when present.
   Title: `title`, else `subject`, else the first `# ` heading, else the file name. The UID comes from the note's path, plus `due` / `event`. A date that does not parse is logged as a problem with the note's path. Dates accepted: `2026-11-15`, `2026-11-15 14:00`, `2026-11-15T14:00:00`, and with `Z` / `+01:00` for an exact instant; a time without a zone is wall-clock (floating), shown at that hour wherever the user is.

Anything that ended more than `past_days` ago is skipped. The plugin never deletes anything by itself: unmarking a note leaves its event (remove it in the pane, or `dav_remove_event`). The pane's Important notes calendar reads every note of the vault (the frontmatter of each, cached by modification time), not only the folders; once such a date was put on the server it shows once (same UID).

## The engine (Rust, `engine/`)

- **The cache** (`store.rs`, schema 2): SQLite in `$ATLAS_PLUGIN_CACHE/calendar.sqlite` — the sources (CalDAV calendars `<account>/<calendar>` with their account, `sub:<name>` subscriptions) with their sync state, the calendar objects as the server has them (text, ETag, UID, a time bound for range queries, the words for search), the contacts. Only a cache: deleting it loses nothing.
- **Pulling** (`pull.rs`, `api.rs pull_all`): every account in turn, each when due (its own clock), its calendars listed again; an account's failure (a refused password, an unreachable host) is its own — the others sync, its cache stays, its card and heading say why; the calendars of an account taken out of Settings are forgotten; each one untouched when its `getctag` did not move; else what changed since its `sync-token` (RFC 6578), else the ETag listing; changed objects fetched with `calendar-multiget` in chunks of 50, gone ones dropped. Subscriptions when due, with `If-None-Match` / `If-Modified-Since`. A background round every minute (`watch`, started by the page) syncs CalDAV every `refresh` minutes (5) and each subscription at its own interval, and tells the page (`changed` event).
- **Recurrence and zones** (`recur.rs`, `zone.rs`): RRULE through the `rrule` crate, counted in the master's frame (dates for all-day, wall clock for floating, the TZID's wall clock otherwise — so 10:00 stays 10:00 across DST); `UNTIL` in any form applied by hand; RDATE, EXDATE (a date EXDATE takes out that day's occurrence), RECURRENCE-ID overrides (moved, retitled, cancelled). TZIDs: IANA names, Outlook's Windows names, Mozilla's prefixed ids, a VTIMEZONE's `X-LIC-LOCATION`, else its standard offset. A DST gap moves a time past the gap.
- **Writing** (`edit.rs`): new events carry the user's TZID and a VTIMEZONE made from chrono-tz's rules (yearly STANDARD / DAYLIGHT parts); changes keep every property they do not touch (attendees, alarms, X- properties) and move SEQUENCE / DTSTAMP / LAST-MODIFIED. "This event" makes or edits an override; "this and following" ends the series with UNTIL and starts a new one (its COUNT reduced by the occurrences before, its later overrides and exclusions moved with it); "all events" shifts the series, its EXDATEs and its overrides' RECURRENCE-IDs by how far the dragged occurrence moved. Writes are conditional (If-Match / If-None-Match); a 412 re-reads the server's version and applies the change to it once. Undo keeps the object's text before each change (in memory, the last 50).
- **Methods** (`api.rs`): the pane's `watch`, `sources` (+ `accounts`, `write`), `range {from, to, sources?, notes?}`, `refresh {force?}`, `create {calendar?, …}`, `update {calendar, href, uid, rid?, scope, …change, move_to?}`, `delete`, `undo {id}`, `quick {text}`, `search {q}`, `test_subscription {record}`; Settings' `suggest_calendars`, `account_status`, `test_account {record}`, `migrate`; the tools above. A write goes through the client of the calendar's own account (`client_for`).
- **Its own Cargo workspace** (`engine/Cargo.toml`, `engine/Cargo.lock` committed): the TLS stack and SQLite stay out of Atlas's build. `engine/build.sh` builds it static (musl, with `musl-gcc` for SQLite and ring) into `bin/x86_64-linux/dav` (ignored by git, as the catalog's).
- The helper is also a command: `echo '{"settings": {…}, "secrets": {"password": "…"}, "tz": "Europe/Madrid"}' | bin/x86_64-linux/dav range`.
- Settings: a tool call brings `settings`; the page passes its own; with neither (the Settings form's `suggest`, the background round) the helper asks `GET /api/plugins` over its pipe. An account's password comes as `params.secrets["accounts.<name>.password"]` (a tool's call and a page's helper call both carry the plugin's secrets), else from the pipe.
- **From 1.0's single account**: flat `url` / `user` and the secret `password` are read as one card named after the server (`cal.example.org` → `cal`) until the page moves them (`main.ts` → `migrate`: the secret copied to `accounts.<name>.password`, the old one left; `accounts` saved, `url` / `user` taken out) — nothing to retype. A `calendar` setting that was a name or an address still resolves.

## Writing to the server: idempotence by UID

- A UID Atlas makes for a date is `atlas-<32 hex of sha256(source, key)>` (`engine/src/uid.rs`); the same source and key always give the same UID, fixed forever (a test pins it). The pane's new events take one from the moment they are made.
- The automatic sync's write (`caldav.rs upsert`): `PUT <calendar>/<uid>.ics` with `If-None-Match: *` → **added**. If it is there: the event carries `X-ATLAS-HASH` (what it says, hashed); the same hash → **unchanged**, a different one → `PUT` with `If-Match: <etag>` → **updated**. A user who moves the event in a calendar app keeps the old hash (apps keep `X-` properties), so the next sync does not move it back unless the note itself changed.
- A UID Atlas did not make (an invite) is first looked up by UID with a `calendar-query` `prop-filter`: RustiCal does not refuse a second resource with the same UID, so without the look-up an invite already accepted elsewhere would be duplicated.
- A UID with characters unsafe in a path (`/`, spaces) is stored as `uid-<hash>.ics`: Radicale answers `%2F` with 403.

## Discovery

`PROPFIND` the address (Depth 0): if it is a calendar, that one; else `current-user-principal` → `calendar-home-set` → Depth 1 listing (name, colour, components, write privilege). An address that answers nothing useful falls back to `/.well-known/caldav` (RFC 6764). RustiCal answers `PROPFIND /` with 405 before asking for credentials, so the 401 for a wrong token only comes from the well-known step; it is reported as such. Redirects are followed by hand, keeping the method. Credentials go with the first request (no 401 round-trip): a server's fail2ban jail may count 401s on `/caldav/`.

Errors are worded for the user: 401 → "app password rejected: … check them in Settings"; 403 → read-only calendar or no rights (with the server's precondition name, e.g. `valid-calendar-data`); 404 → check the address; 405 → is it a CalDAV address?; a network failure names the host and the TLS / DNS cause.

## Example: RustiCal behind Authelia

RustiCal at `https://cal.example.org`, no Authelia at nginx for DAV; devices use Basic + an **app token** made on RustiCal's web page (sign in through Authelia → App tokens). Settings → Calendar → Accounts → Add account: name `home`, address `https://cal.example.org/caldav/` (the top `https://cal.example.org/` also works, through the well-known redirect), user name = the Authelia user name, app password = the token, Test; then *New events go to* among every account's calendars. Contacts are found at `/carddav/` on the same server. RustiCal shows a read-only "birthdays" calendar per address book; hide it with its box if unwanted.

## Not done (follow-ups)

- Sending the iTIP REPLY is Email's (it sends the mail, then calls `import_invite`); following a `METHOD:CANCEL` by itself — deliberately not automatic: the user decides.
- Editing attendees, free/busy look-ups, alarms rung by Atlas.
- The editor's date fields are the webview's own (their order follows its locale, `10/23/2026` in an en-US webview); the hours are typed fields on the 24-hour clock because WebKit's time field ignores `lang`.
